## 摘要
部署在车辆中的大语言模型（LLM）代理必须在每一轮都满足书面操作政策：一个幻觉标识符、遗漏的强制副作用或过早的完成声明都会导致任务失败。我们提出了AgentGuardUtil，这是我们参加CAR-bench Track~1的参赛作品，它将AI规划器（LLM）视为基于现实的验证-修改循环中可能出错的提议者。其核心创新是一个运行时策略编译器：每个对话附带的自然语言策略被编译（每个策略一次）成类型化、可机器检查的规则，其中一部分规则具有可执行形式。一个确定性义务引擎根据实时工具结果和草稿本身的模拟写入后状态来解释这些规则，发出带有计算参数的确切补救调用，而不是自然语言提醒。围绕此引擎，25个确定性门（标识符来源、模式和枚举有效性、先收集后行动、确认和未来时间协议）和一个LLM批评者产生分层发现，驱动一个针对pass k指标调优的有界修订循环。

## Abstract
Large Language Models (LLMs) agents deployed in vehicles must satisfy a written operating policy on every turn: a single hallucinated identifier, omitted mandatory side-effect, or premature completion claim fails the task. We present AgentGuardUtil, our entry to CAR-bench Track~1, which treats the AI planer (LLM) as a fallible proposer inside a grounded verify-and-revise loop. Its core novelty is a runtime policy compiler: the natural-language policy shipped with each conversation is compiled, once per policy, into typed machine-checkable rules, a subset of which receive an executable form. A deterministic obligation engine interprets these rules against live tool results and the simulated post-write state of the draft itself, emitting the exact remedial calls with computed arguments rather than natural-language reminders. Around this engine, 25 deterministic gates (identifier provenance, schema and enum validity, gather-before-act, confirmation and future-time protocols) and an LLM critic produce tiered findings that drive a bounded revision loop tuned for the pass k metric.

## 一、论文的核心问题与整体含义（研究动机与背景）

车载LLM智能体（In-Car LLM Agents）正从研究原型快速走向实际产品，控制车窗、空调、导航、充电等物理世界操作。与一般对话场景不同，这类智能体必须**在每一轮交互中都严格满足制造商制定的书面操作政策**——一旦出现幻觉标识符、遗漏强制副作用或过早声明完成，就可能导致安全事件（如错误理解限速导致碰撞），其后果远超基准分数下降。

当前AI智能体的评估条件与部署环境存在显著差异：现实中的用户请求常不完整或模糊，工具参数可能不可用，且部署环境强加领域特定的政策约束（前提条件、强制副作用、确认要求、披露义务）。CAR-bench基准正是为了捕捉这些部署挑战，从模糊消解（disambiguation）、幻觉拒绝（hallucination）、政策合规执行（base）三个维度评估智能体。

**核心问题**：如何确保基于LLM的车载智能体在每轮交互中严格执行自然语言政策，防止幻觉和遗漏导致的危险操作？

**整体思路**：论文提出AgentGuardUtil系统，采用“学生-教师”分解——LLM（学生）只负责提议行动，一个验证框架（教师）负责审查每个草稿，返回具体发现，在动作到达模拟驾驶员之前重新验证修订。其核心理念是**将自然语言政策编译为可执行规则，将关键检查从模型内部迁移到确定性代码中**，使模型无法绕过或幻觉这些检查。

## 二、论文提出的方法论

### 2.1 核心思想：可验证的“提议-审查-修订”循环

AgentGuardUtil的架构遵循两个互补原则：
- **学生-教师分解**：将提议与批准分离，LLM只提议，验证框架审查，任何动作在执行前必须通过验证。
- **假设-保证纪律**：验证框架只假设学生“有能力但可能出错”，并通过确定性检查承担保证（政策合规、基于观测数据的落地、政策遵守），独立于学生行为。

### 2.2 关键技术细节

#### （1）运行时策略编译器（Runtime Policy Compiler）
- 在对话第一轮，将自然语言政策文本Π编译为类型化规则集R，每个规则r = ⟨id, κ, T_r, ρ⟩带类型（前置条件、自动动作、确认、禁止、披露、约束、选择）、触发工具和命令性要求。
- 复合子句拆分为原子规则（一个条件，一个补救措施）。
- 第二遍将状态条件规则翻译为**可执行形式**：e_r = ⟨g, φ, ◁, v, ω⟩，其中g是读取工具，φ是字段名模式（含通配符），◁是比较操作符，v是阈值，ω是义务模板。
- 编译器看到工具的真实签名，无法验证参数的工具调用会被降级为建议级，**义务引擎只能增加精度，绝不强制无效调用**。

#### （2）确定性义务引擎（Deterministic Obligation Engine）
三步执行流程：

- **第1步：估计动作后环境状态**。利用最近观测σ_g、已执行动作和历史动作，以及草稿拟议动作W_a，计算投影状态σ̂ = π(σ_g; w₁..w_m·W_a)。可预测效果的动作被模拟，不可预测的标记为未知。
- **第2步：计算缺失动作**。对每个活动规则（触发工具已用或出现在草稿中），对每个违反条件的实体，填充动作模板，并移除已执行或已在草稿中的动作，得到Ω——精确的“仍需执行”动作集合。
- **第3步：匹配期望粒度**。如果所有实体都违反条件且工具接受ALL风格参数，则合并为集体动作；镜像检查标记多余动作（对豁免实体执行的动作）和过度聚合动作。

#### （3）分层验证与25个确定性门
- 围绕义务引擎运行**25个确定性门**，每个门检查一个草稿必须遵守的协议。主要门包括：
  - **标识符来源门**：所有不透明标识符必须来自较早的观测结果，防幻觉。
  - **模式有效性门**：参数必须匹配工具的声明类型和枚举值。
  - **先收集后行动门**：规则依赖的观测必须先被获取。
  - **确认协议门**：需要同意操作必须先有用户肯定。
  - **完成门**：声称完成的操作必须实际执行或包含在草稿中。
  - **拒绝-读取门**：告知用户无法做某事前必须先执行相关读取。
  - **未来条件门**：关于未来时刻的问题必须基于未来时刻的数据回答。
- **LLM批评者**只能确认或丢弃建议性发现，不能自行引入发现，也不能覆盖硬性发现。

#### （4）修订循环与防振荡机制
- 每个草稿进入最多R轮的验证-修订循环。
- 硬性发现直接触发修订，建议性发现经LLM批评者过滤后触发修订。
- **振荡阀**：丢弃重复要求学生已修订过动作集的发现，防止两个门之间来回踢皮球。
- **安全网**：修订后仍有硬性发现的草稿，单独对硬性发现再跑一次修订（REVISE_esc）。
- **净化**：剥离无法口语化的标记后，验证过的工具调用和环境回复才到达模拟驾驶员。

### 2.3 算法流程（文字说明）

```
VERIFIED TURN:
1. 首个策略轮次：编译政策→规则集，缓存
2. 提取用户消息中的显式请求加入待办清单
3. 学生LLM采样n次草稿，多数投票选出动作集
4. 进入修订循环（最多R轮）：
   - 运行25个确定性门产生硬性/建议性发现
   - LLM批评者裁决建议性发现
   - 合并分层发现列表F(a)
   - 若F(a)为空则退出，否则带着发现重新提示学生修订
5. 安全网：修订后仍有硬性发现→再修订一次
6. 净化输出，释放验证过的工具调用和回复
```

### 6.2 核心发现

1. **框架的定位是“让好的尝试更好”**：Pass@3提升明显（+13.3个百分点），说明验证框架能有效过滤错误，防止失败到达驾驶员。
2. **不能使三次尝试更相似**：Pass 3提升仅为3.3个百分点，因为学生LLM每次写出不同的草稿，方差仍在。
3. **结构化检查最有效**：幻觉类任务表现最好，因为这是代码可以精确查找的事实（标识符是否出现过、参数是否符合schema）。
4. **模糊消解最难自动化**：代码可以检查是否问了问题、是否得到“是”，但无法判断是否应该问——这需要LLM批评者，而批评者并非总是正确。
5. **主要瓶颈在Pass@3到Pass 3之差**：8个任务在某些尝试中成功但非全部，说明学生的不稳定性是提升Pass 3的关键障碍。
6. **性能成本高但值得**：更高的token消耗并不自动带来更好的评分（全场相关系数r=0.435），但框架的收益来自确定性保障而非更多计算。

## 七、优点

### 7.1 方法论亮点

1. **核心创新：运行时策略编译**——将自然语言政策一次性编译为类型化、可执行规则，这是解决政策合规问题的根本性思路，避免了每轮重新解释政策的不可靠性。
2. **确定性引擎与投影状态模拟**——义务引擎在投影的“草稿写入后状态”上评估规则，能捕获草稿本身创造的新违规（如提案打开所有窗户50%同时开空调，系统会模拟该状态并要求关闭的补偿动作）。
3. **发出精确补救调用**——不是自然语言提醒，而是带着精确参数的、可立即执行的工具调用，消除了学生“回忆政策”的需求，只需“转录更正”。
4. **分层发现机制**——硬性发现确定性触发修订，建议性发现经LLM批评者过滤；批评者只能确认/丢弃，不能自创发现或覆盖硬性发现，保证关键检查不依赖随机判断。
5. **完整的故障保护体系**——振荡阀防止往返震荡，安全网捕获修订引入的新缺陷，内部错误抑制确保缺陷检查不会阻塞合规草稿。
6. **假设-保证纪律**——形式化地从组合验证理论引入设计原则，使系统架构有理论支撑。

- **仅对比基线**：虽然报告了21支队伍中的排名（9–11位），但没有对比其他方法的详细数据，无法全面评估优劣。

### 8.2 方法与架构局限

1. **编译精度限制**：不是所有政策规则都能编译为可执行形式——无法验证参数的工具调用被降级为建议，这意味着部分政策保障依赖LLM批评者，而这些保障不够可靠。
2. **模糊消解是明显短板**：代码无法判断“是否应该问澄清问题”，该判断只能交给LLM批评者，而批评者并非总是正确。这本质上是LLM判断力的问题，而非可验证程序逻辑问题。
3. **成本高昂**：每轮验证的token消耗是基线的4.4倍，时间消耗是6倍。对于车载实时交互场景，19.2秒/轮的开销可能是实际部署的障碍。
4. **学生不稳定是未解决的问题**：Pass 3与Pass@3的巨大差距（53.3% vs 80.0%）表明框架无法消除学生的逐次方差，而只是过滤了错误。框架的保障对“未被编译规则覆盖的任务”保持沉默。
5. **无训练/微调**：框架完全依赖提示工程和确定性代码，可能错过端到端优化的机会。
6. **依赖工具schema和观测数据的质量**：如果工具文档不完整或观测延迟/不准确，投影状态估计可能失真。

- 以CAR-bench单一基准评估，可能对特定工具集和协议过拟合
- 隐藏测试集的规模限制，可能掩盖了在其他场景的失败模式
- 评估仅覆盖车载领域，方法在其他物理世界动作场景（机器人、家居等）的适用性未验证
