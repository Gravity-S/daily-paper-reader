## 摘要
长周期安全LLM代理必须在许多相互依赖的交互中携带信息和决策，后续行动往往依赖于更早发现的服务、状态或访问权限。这使得最终任务的成功难以解释：代理可能在达到目标能力可被执行的环节之前就已失败。我们提出了一种诊断方法，通过检查点来标记安全任务，区分能力暴露前后的失败，并使用受控干预来测试可疑的上游瓶颈。我们评估了该方法在四个任务族中的表现，这些任务涉及延迟重用发现的信息、重用观察到的状态、从失败策略中恢复以及不确定结果后的决策。在观察状态重用方面，检查点分析表明，Gemini 2.5 Flash的许多失败发生在模型观察到后续预期重用的状态之前。在一项预先设定的92种子研究中，针对性的协议消歧指导将状态观察率从匹配的非指导对照组消息下的65.5%提高到95.4%。使用Gemini 3.7 Flash重复相同的实验设计产生了相反的效果，而状态观察不再可靠地预测任务完成情况。这些结果表明，主要的失败来源可能会随模型代际而转移，这促使评估应诊断长周期安全代理在何处及为何失败，而非仅依赖总体任务成功率。

## Abstract
Long-horizon security LLM agents must carry information and decisions across many dependent interactions, where later actions often depend on services, state, or access discovered much earlier. This makes final task success difficult to interpret: an agent may fail before it ever reaches the point where the capability of interest can be exercised. We present a diagnostic methodology that instruments security tasks with checkpoints, separates failures before and after capability exposure, and uses controlled interventions to test suspected upstream bottlenecks. We evaluate the methodology across four task families involving delayed reuse of discovered information, reuse of observed state, recovery from failed strategies, and decision making after uncertain outcomes. On observed state reuse, checkpoint analysis shows that many Gemini 2.5 Flash failures occur before the model observes the state it is later expected to reuse. In a pre-specified 92-seed study, targeted protocol-disambiguation guidance increases state observation from 65.5\% under a matched non-guidance control message to 95.4\%. Repeating the same design with Gemini 3.7 Flash produces the opposite effect, while state observation no longer reliably predicts task completion. These results show that the dominant source of failure can shift across model generations, motivating evaluation that diagnoses where and why long-horizon security agents fail rather than relying only on aggregate task success.

## 1. 核心问题与整体含义（研究动机和背景）

- **核心问题**：长周期（Long-Horizon）安全LLM代理的**端到端任务成功率**难以解释失败根源——代理可能早在目标能力（如状态复用、策略恢复）可被检验之前就已失败，导致最终失败被误归因于下游能力缺陷。
- **背景**：现有LLM代理在渗透测试、Web漏洞利用、CTF等安全任务中表现日益增强，但已有基准（如Cybench、AutoPenBench等）虽引入中间里程碑或阶段指标，仍无法回答"代理是否真正到达了目标能力可被执行的节点"。
- **关键区分**：端到端失败包含两种截然不同情形：
  - **上游失败**：代理未能到达能力可被检验的节点（即"能力暴露"前失败）；
  - **下游失败**：代理到达暴露点后，执行目标能力时失败。
- **核心主张**：评测不应仅报告"是否成功"，更应诊断"在哪里失败、为何失败"，尤其是长周期任务中依赖链长、状态传递复杂，可靠性问题更为突出。

## 2. 方法论：核心思想与关键技术细节

### 2.1 核心思想
采用**检查点（Checkpoint）**将任务分段，判定代理是否到达"能力暴露"（Exposure）门控检查点，从而将失败拆分为"暴露前"与"暴露后"两个阶段，并用**受控干预**（Rescue–Placebo对照）验证上游瓶颈的因果性。

### 2.2 关键技术细节

- **诊断任务设计**：
  - 每项任务包含：确定性种子生成器、Docker化多服务环境、固定提示词与工具协议、检查点规范（映射轨迹证据到任务进度）；
  - 预验证每个任务存在合法解，保证流程在冻结配置下可行。
- **检查点与暴露条件分析**：
  - 检查点仅在轨迹中实际出现证据时计分（如命令输出或服务响应），尝试相应动作不算达成；
  - 每个能力对应一个**门控检查点**（如CSR的C3：精确观察生成的待复用状态）；
  - 报告三种指标：端到端成功率、门控检查点到达率、到达暴露后成功率。
- **受控干预**：
  - 每个环境种子运行三组：**Baseline**（无额外消息）、**Rescue**（提供针对可疑瓶颈的定向信息）、**Placebo**（字节/行数配平的无任务相关信息）；
  - 对比Rescue vs. Placebo为主分析，隔离信息内容效应与一般性消息注入效应；
  - 干预内容不泄露任务关键值（如配置工件、生成状态、凭据等），仅移除指定上游障碍。
- **统计方法**：
  - 主要比较使用**双侧精确 McNemar 检验**（配对二值结果），α = 0.05；
  - 样本量基于配对功效分析（正常近似与精确枚举双重校验）。
- **实验治理与可复现性**：
  - 预注册：正式实验前冻结运行顺序、任务配置、干预内容、分析计划；
  - 使用加密摘要绑定关键输入（scaffold配置、干预消息），防止事后更改；
  - **追加式账本（append-only ledger）**记录每次运行生命周期，基础设施失败与科学任务失败分开记录，不静默重跑。

## 3. 实验设计：数据集、场景与对比方法

### 3.1 任务族（Benchmark 场景）

| 任务族 | 变体 | 研究焦点 |
|--------|------|----------|
| Delayed Secret Reuse (DSR) | Short、Long | 延迟秘密复用（次级证据） |
| Controlled State Reuse (CSR) | Short、Medium、Long | 受控状态复用，中间动作数分别为2、8、20（主任务） |
| Strategy Recovery (SR) | Control、Explicit、Ambiguous | 策略失败后的恢复 |
| Ambiguous-Outcome Adaptation (AOA) | Transient、Persistent、Explicit | 不确定结果后的决策 |

### 3.2 模型与运行配置

- **对比模型**：Gemini 2.5 Flash、Gemini 2.5 Pro（跨模型初始评估）；Gemini 2.5 Flash vs. Gemini 3.7 Flash（跨代复制研究）。
- **运行限制**：最多90个执行命令、120个模型轮次、连续12个协议错误终止、命令超时30s、请求超时60s、输出上限1024 tokens。

### 3.3 实验流程三阶段

1. **初始特征化**（描述性）：CSR每模型15次运行（5 seeds × 3变体）、AOA每模型10次、SR共30次、DSR共10次；

3. **验证性干预研究**：
   - Gemini 2.5 Flash：92个新种子，276个计划运行（92×3），有效配对87对（5个placebo基础设施无效）；
   - Gemini 3.7 Flash：同一冻结设计复制，91个有效配对。

## 6. 主要结论与发现

### 6.1 核心发现
1. **Gemini 2.5 Flash在CSR上的多数失败发生在能力暴露之前**：端到端成功率仅33%（5/15），但C3状态观察到达率仅40%（6/15），且到达C3后成功率为5/6（83%）。Gemini 2.5 Pro则全部15次成功且全部到达C3。
2. **协议发现是Gemini 2.5 Flash暴露瓶颈的因果因素**：在92种子验证性研究中，Rescue使C3到达率从Placebo的65.5%（57/87）提升至95.4%（83/87），McNemar p = 2.56×10⁻⁶；且到达C3后，205/210（97.6%）的运行能完成剩余流程。
3. **跨代际反转**：Gemini 3.7 Flash重复同一实验，Rescue的C3到达率（79.1%）反而显著低于Placebo（98.9%），19/20不一致配对倾向Placebo方向（p = 4.01×10⁻⁵）；且到达C3后仅36.1%最终成功（对比Gemini 2.5 Flash的97.6%），说明该模型的主要失败已迁移至下游。
4. **端到端成功率掩盖了任务设计的局限性**：DSR存在混淆变量、SR无失败可诊断、AOA未触及目标分支——这些仅凭最终成功率无法察觉。

### 6.2 方法论启示
- 评估应同时报告端到端成功率与暴露条件化结果；检查点用于定位失败，受控干预用于验证因果解释；
- 一个模型代际中确认的瓶颈不应想当然迁移至下一代模型。

## 7. 优点

- **方法论创新性强**：首次系统区分"能力暴露前"与"暴露后"失败，避免了长周期安全任务中常见的失败归因错误。
- **因果验证严谨**：Rescue–Placebo配对设计配合精确McNemar检验，比单纯轨迹分析有更强的因果说服力。
- **预注册与冻结管线**：通过实验治理机制（manifest冻结、加密摘要、追加式账本、基础设施失败分离）保证了可复现性和分析诚实性。
- **跨代复制视角新颖**：用同一冻结实验检测模型代际变化，发现了干预方向反转这一反直觉且重要的现象，凸显动态评测的必要性。
- **任务设计强调变量隔离**：CSR通过仅改变中间动作数（2/8/20）实现精密的受控比较，为长周期能力评测提供了范式。

## 8. 不足与局限

- **任务覆盖不均衡**：四个任务族中只有CSR提供了干净、可统计的因果证据；DSR有混淆变量，SR存在上限效应，AOA未到达目标分支，削弱了方法论"通用性"的论证。
- **探索性阶段样本量过小**：初始特征化每条件仅5次运行，部分差异可能与随机性相关，作者虽未过度解读但仍值得注意。
- **模型覆盖有限**：仅评估Gemini系列（2.5 Flash/Pro、3.7 Flash），未涉及其他主流模型（如GPT、Claude、开源模型等），外部效度受限。
- **合成环境局限**：所有任务在确定性Docker环境中运行，虽然有利于对照，但与真实网络安全场景的复杂性和不确定性差距明显。
- **未解释Gemini 3.7 Flash下游失败的具体原因**：论文仅指出其主要失败已移至状态观察之后，但没有进一步定位这一新的瓶颈。
- **干预设计的特殊性**：Rescue消息本质上包含"协议消歧"提示，其反向效果在Gemini 3.7上未被深入分析（如是否干扰了模型原有策略），缺乏解释性实验。
- **缺乏跨模型/跨任务的干预泛化检验**：未将同类干预应用于其他模型或任务来验证机制普适性。
