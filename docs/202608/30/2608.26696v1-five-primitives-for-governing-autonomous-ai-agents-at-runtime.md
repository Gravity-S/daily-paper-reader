## 摘要
企业部署的自治AI代理继承了一种为人类用户和长期服务设计的控制模型，但该模型在三个方面具体失效：代理主体是短暂的，出现和消失的速度快于供应；它们的行为由模型而非程序选择，因此可能尝试的行为集合事先未知；代理群体是发现的而非供应的，因为任何能调用API的人都可以创建一个。我们认为，治理此类代理是一个运行时问题——既不是模型对齐问题，也不是构建时问题——我们根据行动生效前及生效后必须回答的问题推导出五种原语：发现、身份、治理、证明和供应链。对每一种原语，我们说明若其缺失会出什么问题，以及为何其他原语在结构上无法替代。我们描述了一种实现，在该实现中，代理的行为在生效前根据策略进行调解，根据每租户操作词汇表进行授权，并记录在哈希链式的签名账本中，第三方可在供应商不参与的情况下进行验证。我们报告了该架构的代价：执行点位于请求的关键路径上，身份要求每个工作负载有边车，且故障关闭式调解将可用性事件转化为拒绝。我们明确说明实现状态：四种原语已构建并正在私有试点中运行，第五种已作为独立工具构建但尚未集成到请求路径中。我们有意将其保留在集合中：一个与作者恰好构建的内容完全匹配的五部分分解并非分类法，而是对代码库的描述。

## Abstract
Enterprise deployments of autonomous AI agents inherit a control model built for human users and long-lived services, and the fit fails in three specific ways: agent principals are ephemeral, appearing and vanishing faster than provisioning; their actions are selected by a model rather than programmed, so the set of things they may attempt is not known in advance; and the population is discovered rather than provisioned, because anyone who can call an API can create one. We argue that governing such agents is a runtime problem -- not a model-alignment problem and not a build-time problem -- and we derive five primitives from the questions that must be answered before an action takes effect and after it has: discovery, identity, governance, attestation, and supply chain. For each we state what fails if it is absent and why the others cannot structurally supply it. We describe an implementation in which an agent's action is mediated against policy before it takes effect, authorised against a per-tenant action vocabulary, and recorded in a hash-linked signed ledger a third party can verify with the vendor out of the loop. We report what the architecture costs: the enforcement point sits on the request's critical path, identity requires a sidecar per workload, and fail-closed mediation converts availability incidents into denial. We are explicit about implementation status: four primitives are built and running in private pilots, and the fifth is built as separate tooling and not yet integrated into the request path. We keep it in the set deliberately: a five-part decomposition that exactly matches what its authors happened to build is not a taxonomy but a description of a codebase.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：企业部署的自治AI代理（autonomous AI agents）继承了一套为人类用户和长期运行服务设计的控制模型（身份提供者、RBAC、API网关、审计日志），但这套模型在三个关键维度上无法匹配代理的特性：
  - **主体短暂性（ephemeral principals）**：代理可能仅为单个任务而存在，出现和消失的速度远快于供应（provisioning）流程。任何依赖人工预先注册的控制机制要么被跳过，要么成为瓶颈。
  - **行为非预编程性（model-selected actions）**：代理的行为由模型在运行时从工具集中选择并组合参数，而非由代码预先定义。政策作者无法事先枚举代理可能尝试的所有操作。
  - **种群动态发现性（discovered, not provisioned）**：任何能调用API的人都能创建代理，企业内部代理群体是动态测量的"事实"，而非人工维护的清单。只治理已知代理的系统，治理的只是"合规子集"，而非真正需要治理的对象。
- **核心论点**：代理治理本质上是**运行时问题（runtime problem）**，而非模型对齐问题（对齐是模型属性，权威是部署属性）或纯构建时问题（静态分析无法约束模型在调用时刻组合参数的行为）。
- **整体含义**：论文主张在现有控制层之上新建一个运行时治理层，回答行动生效前和生效后的关键问题，并由此推导出五种不可约的原语。

## 2. 论文提出的方法论

论文提出并详细论证了五种运行时治理原语，每个原语对应一个必须回答的问题：

1. **发现（Discovery）** —— "代理是否存在，我们是否知道它？"
   - 两半组成：
     - **能力发现（capability discovery）**：代理尝试平台未定义的行动时，该尝试本身即是信号。在默认拒绝（deny-by-default）机制下，拒绝与发现是同一事件。
     - **种群发现（population discovery）**：通过扫描代码、部署清单、网络行为来枚举代理。
   - 三个记录规则：
     - **聚合而非追加**：每个（组织，行动类型）只保留一行（upsert），防止代理重试循环导致表格无界膨胀。
     - **只存名称不存值**：未分类操作的字段可能含敏感值，只存储参数名，表结构不提供可存储值的列。
     - **记录是观测而非治理**：记录失败不得影响已做出的拒绝决定，发现机制不得具备拒绝能力。

2. **身份（Identity）** —— "它可证明地是什么？"
   - 使用基于证明的工作负载身份（attestation-based workload identity，借鉴SPIFFE），基于工作负载自身无法选择的属性（是什么、运行在哪、在哪个服务账户下）签发短期凭证。
   - 三个关键设计要点：
     - 身份在**传输层**呈现（mutual TLS），而非在payload中断言，防止代理自称身份。
     - 一个主体需要多套词汇表（存储、审计、政策），依靠规范映射保持可追溯性。
     - 某些内部代理身份应从已有数据**派生**而非存储。

3. **治理（Governance）** —— "它是否被允许这样做（在行动生效前决定）？"
   - 调停者（mediator）位于请求路径上：代理请求 → 策略引擎决定 → 代理执行或停止。
   - 关键特性：
     - **每租户、客户自建的操作词汇表**：供应商无法预先枚举代理可能尝试的行动，词汇表必须可扩展，且定义需不可变版本化，审计记录指向当时的版本。
     - **默认拒绝（deny-by-default）**：未被任何政策允许的行动一律拒绝；但需注意，这仅保护授权，不保护披露（政策评估所需的参数可见性需单独处理）。
     - **终止开关（kill switch）**：在每次授权请求时查询，使撤销在下一个动作生效而非等到凭证过期。

4. **证明（Attestation）** —— "发生了什么（以他人可验证的形式）？"
   - 每次授权决策写入仅追加账本：哈希链式链接、规范化、用每租户密钥（存于KMS、永不导出）签名。
   - 验证器必须运行在供应商系统之外，客户可导出证据包并用独立工具离线验证。
   - 完整性声明必须明确覆盖窗口；无法确定完整的字段必须默认为false。
   - 诚实的残余风险：拥有数据库和签名权限的操作员理论上可重写并重签历史，链提供的是**重写的证据**而非预防。

5. **供应链（Supply Chain）** —— "它由什么构成，是否发生了变化？"
   - 代理是模型、框架、工具集、依赖树、容器镜像的组合，每个元素都是供应链风险面。
   - 与其他四个原语不同，它不在请求路径上，而是在请求之间被验证/失效。
   - 与常规软件相比更严重的三个特性：
     - 信任决策在部署时一次性做出，但持续消费，而组合可能在请求间改变。
     - 组成包含**模型、提示模板、工具描述**——修改工具描述可在不触代码的情况下改变代理行为。
     - 责任归因穿越边界：有害行动源于模型决策还是被操纵的工具描述/被攻陷的依赖，需要其他四者不收集的溯源。

**各原语的不可替代性论证**：发现解决"不主动出现的代理"问题；身份解决"自称为X"的问题；治理解决"有身份无约束"的问题；证明解决"系统自证其决定"的问题；供应链解决"受损物表现正常"的问题。去掉任何一个，其余四个都无法在结构上补位。五个原语具有独立的信任模型、失败模式和时标，合并它们会继承各自最差的失败模式。

**实际实现形态**：一个代理代理通过相互TLS调用 POST /v1/actions/authorize（携带工作负载凭证），管理服务器包含调停者（策略评估+行动目录）、证明工厂及后台验证器，身份服务驱动工作负载身份平面，状态存于关系数据库（仅追加链）+ KMS签名密钥。代理框架暴露五个钩子：身份提供者、行动调停者、证明宿、终止开关源、治理上下文。

## 6. 论文的主要结论与发现

- **治理自治AI代理是运行时问题**，核心驱动力正是使代理有用的三个特质（短暂性、自选行为、无供应繁殖）——它们恰好击败了为"已供应主体"设计的控制。
- **五原语分解是必要且充分的**：必须回答"存在吗、是什么、可以吗、发生了什么、由什么组成"五个问题；每个原语都必要，彼此在结构上不可替代，且失败模式显著不同。
- **发现原语的具体设计准则**：聚合而非追加（防代理重试放大为DoS）；存名称不存值（对未分类数据的最小化披露）；记录失败不得改变已做出的拒绝决定。
- **身份验证必须在传输层而非载荷层**，否则代理可选择自己的主体；每租户行动词汇表使审计语义需要不可变版本化。
- **默认拒绝保护授权但不保护披露**——两个决定共享一个控制面但只有一个有安全网，这是一个架构邀请的失误。
- **证明的价值取决于验证器的位置**：验证器必须在供应商的系统之外运行；完整性字段无法确定时必须默认为false。
- **治理层必须能治理自身**：内部代理与客户代理走完全相同的路径（同一身份平面、同一授权端点、同一终止开关、同一证明链），内部行动类型通过传输层身份检查而非命名约定来强制隔离——这删除了整个"特权例外"类别的问题。
- **成本清单**：关键路径延迟（网络往返+策略评估+持久化写入）、每工作负载边车（采用最大障碍，且是内在而非偶然的）、故障关闭将治理层故障转化为所有代理的拒绝（这是正确的权衡但真实的成本）、前端加载集成成本（首个代理成本高但第十个代理边际成本很小）。
- **适用边界**：当行动集小、固定、可预先枚举，单一信任域、无外部对手方、证据无需第三方验证时，进程内护栏更简单更合适。

- **"构建并被现实修正"的元方法论**：从真实失败（验证器报告就绪但验证无物、就绪门不可能变false）中总结出"信号来自缺乏负值而非存在正值"的领域教训，对治理系统验证方法有普适意义。

## 8. 不足与局限

- **无定量评估**：作者明确承认不是评估论文，无跨部署群体的测量结果，无延迟开销/BOM/成本的量化数据。五原语的"充分性"在逻辑上论证了必要性，但未从经验上证明其覆盖了真实部署中的全部需求。
- **试点范围过小**：仅"少量私有试点"，不足以支撑对外部组织多样性（行业、规模、合规要求）的结论。供应链原语完全未在控制平面验证，使得"五原语分解"的实证基础实际上是"四原语"。
- **供应链原语的"预定论"嫌疑**：作者把"保持第五个原语"辩称为原则（"匹配作者恰好构建内容的分解不是分类法"），但这也可能被解读为将未完成工作包装进理论框架——尽管作者提前声明了这只是路线图事实而非论点，但读者仍需自行判断保留是否合理。
- **供应链归因难题未解决**："模型选择不佳 vs. 工具描述被操纵 vs. 依赖被攻陷"的归因区分需要其他四者不收集的溯源，论文指出了问题但没有给出答案。
- **拒绝-发现合一的副作用**：将"拒绝"作为"发现"信号在默认拒绝配置下工作良好，但一旦词汇表逐步完备，未定义行动的比例下降，发现信号的触发比率也会下降，该机制随系统成熟度而衰减的规律未被讨论。
- **身份模型的信任根**：基于证明的工作负载身份依赖平台自身属性的可信性。"平台属性不能被工作负载自行选择"这一假设在容器被攻陷场景下可能失效（工作负载可从内部伪造部分属性），论文未讨论这个信任根被攻破时的降级路径。
- **故障关闭的真实代价可能被低估**：论文认为"故障关闭比故障开放正确"，但将治理层可用性要求提高到所治理最关键系统的水平，在实践中的运营成本（SLO、冗余、故障演练）远超过文中所言"集成成本前置"的程度。
- **适用场景受限**：方案针对企业级、多信任域、有外部验证需求的场景；对小型团队/低风险场景（行动集固定、单一信任域）明确不适用，但未尝试覆盖这些场景的替代方案对比。
