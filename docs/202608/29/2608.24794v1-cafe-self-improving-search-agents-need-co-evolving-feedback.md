## 摘要
结果监督的搜索智能体能够学习何时以及如何检索证据，但终局奖励既不能定位中间错误，也不能在错误累积之前重定向正在进行的轨迹。将纠正性反馈视为一种学习到的轨迹内干预，将两个角色耦合在一起：智能体必须决定何时请求并使用反馈，而评论者必须从结果混淆的轨迹中推断出有用的纠正，这些轨迹的失败模式随着智能体的改进而变化。我们提出了CAFE（耦合智能体-反馈进化）框架，其中共享参数模型在搜索智能体和评论者角色之间交替。CAFE首先从围绕基础智能体自身失败构建的轨迹中初始化反馈条件的恢复，然后耦合在线和离线优化。在在线强化学习期间，比较性反馈估计使用提示级别的调用-跳过成功差距来塑造请求回报，而反馈感知的优势塑造在反馈前后重新加权令牌优势。在离线阶段，从轨迹派生的偏好优化从匹配的成功和不成功轨迹中学习反馈。在七个智能体搜索基准上，CAFE平均优于所评估的基于强化学习的搜索智能体，在所有六个域外基准上保持其收益，并减少了答案级幻觉。单侧消融表明，仅改进智能体或仅改进评论者最终会达到平台期，而交替两种更新则持续提高性能。这些发现表明，自我改进的搜索智能体需要与其引导的策略共同进化的反馈。

## Abstract
Outcome-supervised search agents learn when and how to retrieve evidence, but terminal rewards neither localize intermediate errors nor redirect an ongoing trajectory before those errors compound. Treating corrective feedback as a learned in-trajectory intervention couples the two roles: the agent must decide when to request and use feedback, while the critic must infer useful corrections from outcome-confounded rollouts whose failure patterns shift as the agent improves. We introduce CAFE (Coupled Agent--Feedback Evolution), a framework in which a shared-parameter model alternates between search-agent and critic roles. CAFE initializes feedback-conditioned recovery from trajectories built around the base agent's own failures, then couples online and offline optimization. During online RL, a comparative feedback estimate uses a prompt-level call--skip success gap to shape request returns, while feedback-aware advantage shaping reweights token advantages before and after feedback. Offline, rollout-derived preference optimization learns feedback from matched successful and unsuccessful trajectories. On seven agentic search benchmarks, CAFE outperforms the evaluated RL-based search agents on average, retains its gains across all six out-of-domain benchmarks, and reduces answer-level hallucinations. One-sided ablations show that improving only the agent or only the critic eventually plateaus, whereas alternating the two updates continues to improve performance. These findings suggest that a self-improving search agent needs feedback that co-evolves with the policy it guides.

## 1. 核心问题与整体含义（研究动机和背景）

- **核心问题**：结果监督（outcome-supervised）的搜索智能体虽然能学习何时检索证据，但**终局奖励（terminal reward）只能给出正确/错误的二元信号，既无法定位中途的具体错误步骤，也无法在错误累积破坏整条轨迹之前进行即时干预**。
- **现有方法的缺陷**：像信息增益、置信度变化、局部状态比较等更细粒度信号，本质上仍是“评价性”（evaluative）而非“指导性”（instructive）的——它们只能事后归因，不能在现场纠正正在偏离的轨迹。而 Reflexion、Self-Refine、CRITIC 等自然语言反馈方法，往往依赖提示词驱动的非训练模型进行事后批判，未与训练流程深度耦合。
- **引入反馈带来的三重耦合挑战**：
  1. **智能体侧**：何时请求反馈（学习问题）？成功被反馈“救回”的轨迹与完美轨迹奖励相同，如何正确地归因作用？
  2. **评论者侧**：没有 ground truth 的反馈本身，其质量被前置搜索和后继动作共同混淆，如何从稀疏结果中学习生成有效反馈？
  3. **两者之间**：在线更新会改变智能体访问的状态和失败模式——一个静态评论者会与它所指导的不断演化的策略脱节。
- **核心主张**：自我改进的搜索智能体需要的是**与其策略共同进化（co-evolve）的反馈**，而非一个绑死于早期失败分布上的固定监督者。

## 2. 方法论：CAFE 核心思想、技术细节与算法流程

### 2.1 总体框架：共享参数、双角色交替

- 用一个**共享参数模型**同时充当**搜索智能体（agent）** 和**评论者（critic）** 两种角色，通过角色条件（role-conditioning）切换：
  - 智能体在任意中间历史状态 `h_{i,t}` 可输出 `<request_feedback>` 动作；
  - 模型随即切换为评论者角色，基于当前轨迹生成纠正性反馈 `f_{i,t}`，追加到上下文后交还控制权给智能体角色，继续 rollout。

### 2.2 阶段一：反馈增强 SFT 初始化（bootstrap）

- 收集基础智能体的**失败轨迹**，由教师模型（Kimi-K2.5）定位最早出错的轮次；
- **保留错误前缀**，插入 `<request_feedback>` 动作，由教师生成反馈及反馈条件下的**成功续接**，构成训练样本（只有修复后达到正确答案的轨迹被保留）；
- 与纯教师演示不同，这些轨迹保留了基础智能体**真实访问过的状态**和失败模式，为后续学习提供高质量初始化。

### 2.3 阶段二：在线智能体优化——反馈感知的信用分配

面对“反馈是否值得请求”和“请求成功该归因于哪段行为”两个问题，CAFE 设计了两个组件：

- **比较性反馈估计（CFE, Comparative Feedback Estimate）** ：
  - 在 GRPO 的 rollout 组内，将轨迹分为“调用反馈组”与“跳过反馈组”，计算两组经验成功率的**提示级差距** `û(x)`（见公式 2）；
  - 最终奖励包含三个项：任务项 `r_task`（原始正确性奖励）、反馈项 `r_fb = β·C·û`（调用了反馈则附加组级差距）、重复惩罚项 `r_repeat`（惩罚第二次及以上的冗余请求）；
  - 在单侧缺失时使用 batch 级后备估计（fallback）。
- **反馈感知优势塑造（Feedback-Aware Advantage Shaping）** ：
  - 将调用反馈的轨迹按首个请求点切分为**反馈前（pre）令牌、请求令牌、反馈后（post）令牌**三部分；
  - 反馈前令牌优势**降低**（`max(A_i − λg, 0)`），反馈后令牌优势**提高**（`A_i + λg`），仅当 `A_i > 0` 且 `g_i > 0` 时生效（公式 5）；
  - 原因：SFT 初始化中请求往往紧随已出错的片段之后，统一强化会奖励需要被放弃的坏行为。

### 2.4 阶段三：离线反馈优化——rollout 派生的偏好优化（RDPO）

- 从最新在线 rollout 中，按 prompt 分组，配对**成功调用反馈的轨迹**与**失败轨迹**；
- 用 token 集 Jaccard 相似度（阈值 τ=0.7）过滤得到“首个请求点之前历史相似”的配对，再经 LLM 判断质量筛选；
- 以成功轨迹的历史为共享上下文，**偏好成功反馈、拒绝失败反馈**，执行 DPO 式更新；
- 相比仅使用正样本的 rollout 派生 SFT（RSFT），RDPO 通过成对比较消除结果混淆，更干净地指示反馈质量。

### 2.5 迭代共演化算法流程（Algorithm 1 概括）

1. 基础模型 → 对失败轨迹做反馈增强 SFT → 得到共享初始化 θ₀；
2. 对 k=0…K−1 循环：
   - 在线阶段：采样 n 条/提示的 rollout → 计算 CFE 回报与塑造后优势 → GRPO 更新 θ → 得到中间检查点 θ_{k+½}；
   - 离线阶段：从本轮 rollouts 中挖掘配对偏好数据 → RDPO 更新共享模型 → 得到 θ_{k+1}；
3. 返回共演化的共享模型 θ_K。

### 2.6 理论保障（保护任务更新方向）

- 论文给出一个定理（Theorem 1）：当 CFE + 优势塑造带来的更新扰动足够小（`Δ_CAFE < ‖G_task‖`），CAFE 的在线更新与原始的纯结果 GRPO 任务更新保持**正内积**——即不会反向优化任务目标。

## 6. 主要结论与发现

- 在 7B 规模下，CAFE 在平均 EM/F1 上达到**所有评估方法中的最强平均 EM（52.5）与第二高平均 F1（60.7）**，较最强 RL 基线（IGPO）提升 2.1 EM 和 1.3 F1；
- 相对于 GRPO 基线，CAFE 在**全部七个基准**上均有提升（包括全部六个域外数据集），证明反馈纠正中间错误的能力在多跳任务上收益最大（如 MuSiQue、Bamboogle）；
- 3B 规模下同样稳定超越既有 3B 搜索智能体基线，接近部分 7B 基线水平；
- 在 BrowseComp-Plus 深度研究场景中呈现同样递增的训练收益曲线（EM 4.4→5.3→6.8→7.7）；
- **幻觉率显著下降**：基础模型 29.9% → GRPO 17.6% → CAFE 12.6%（每个基准上都优于 GRPO）；
- **共演化是根本因素**：单侧更新（只更新 agent 或只更新 critic）均会趋于平台期（agent-only 最终 83.6，feedback-only 仅 71.3），交替更新可持续提升（86.6）；
- **跨玩分析表明增益来自“阶段匹配”而非“评论者绝对能力”**：同一迭代的 agent-critic 配对总是最优；固定最终 agent，用 SFT critic 换为迭代 5 的 critic，EM 从 80.6 提至 84.0。
- 反馈内容随训练演化：早期关注检索/接地错误（如误读结果、实体混淆），中期聚焦证据验证（如 valid answers、explicitly stated），后期转向高层规划与执行效率（如 repeated query、redundant tool calls、logic fails）——证明评论者确实在跟随策略失败的演化轨迹。

## 8. 不足与局限

1. **理论保证有限**：定理 1 只在“扰动足够小”的条件下成立。实验中的引导强度（β=0.5、λ=0.5）未见敏感度分析，极端取值下方向保持性质可能失效；
2. **SFT 依赖教师模型**：初始反馈数据需要外部强教师（Kimi-K2.5）帮助标注最早错误位置并生成修复，对教学模型的依赖未展开讨论，可能引入该模型的偏差；
3. **反馈耦合导致的归因残余偏差**：虽然 RDPO 通过前缀匹配降低结果混淆，但 Jaccard 相似度阈值（0.7）和 LLM 判断筛选并不能完全消除语义层面不匹配的配对，仍可能含噪声；
4. **评估规模有限**：主实验大多基于 500 样本/数据集，BrowseComp-Plus 的数字相对较低（EM 7.7），在更广泛、更具挑战性的真实场景中的效果仍有待验证；
5. **基线可比性**：Search-R1、R-Search 引用了原论文报告的数字（而非在统一检索环境下的复现），潜在环境差异可能影响对比公平性；IGPO 虽是复现，但初始化基于 CAFE 的 SFT checkpoint，可能给 CAFE 带来隐性不公平优势；
6. **计算开销**：每次迭代抽样 8 条轨迹/提示、500 步在线 RL + 5 轮 RDPO，在 8×A100 上耗时约两天，成本较高；实际部署到更大模型（如 70B/几百B）时开销可能显著放大；
7. **幻觉评估方法**：答案级幻觉判定为自动规则（含至少一个无证据支撑的事实即算幻觉），其精确性与人类判断一致性未完成校准报告；
8. **可解释性欠缺**：反馈学习过程本身是黑盒的，虽然案例研究和术语演化可视化了反馈行为变化，但对于“为什么在特定状态请求反馈是最优”缺乏严格的形式化分析；
9. **搜索环境单一**：仅用 E5 检索器 + 本地固定语料，未见对不同检索器、不同语料组合的扩展测试，反馈机制的迁移性在不同环境间可以进一步验证；论文也没有讨论真实在线搜索 API 场景下反馈机制是否对接口延迟、噪声、动态内容比例等变得敏感。
