## 摘要
AI 智能体日益编排与用户、工具和系统资源交互的长时程活动，持续数天乃至数周。为提高智能体质量、安全性和成本效率，开发者需要确定故障发生在哪里、什么触发不安全效应，以及哪些任务消耗最多预算，然后优化这些任务。在系统软件中，性能剖析通过聚合资源消耗并将其归因于负责的代码路径以识别热点，从而回答类似问题。然而，现有智能体可观测性工具侧重于单次执行的调试与追踪，而非跨运行、长期的性能剖析，这使得这些问题难以大规模回答。智能体可观测性不仅需要调试，还需要性能剖析，但剖析智能体颇具挑战：负责的实体是诸如“诊断身份验证”“比较分支”之类的任务意图，而非代码路径，并且缺乏用于聚合的稳定标识符。我们提出一种语义操作栈模型，将性能剖析适配到智能体轨迹。统一操作表示所有活动，操作栈取代运行时调用栈，从而支持不同粒度下的层次化归因。我们观察到，智能体的任务占据一个连续区间，并可分解为子任务，因此我们引入递归操作分割，它按任务边界递归地切分轨迹。AgentPProf 是一种剖析器，可将智能体轨迹聚合为与 pprof 兼容的剖析数据，从而支持火焰图可视化与分析。AgentPProf 在 CodeTraceBench 上相对于人工标注达到 0.764 $B^3$ F1。在三个问题定位基准上，该剖析将 MAP 最高提升 56%，表明其能以实用的剖析开销有效地进行资源归因、定位问题并帮助优化 token 成本。AgentPProf 可在 https://github.com/eunomia-bpf/agentsight 获取。

## Abstract
AI agents increasingly orchestrate long-running activities with users, tools, and system resources for days and weeks. To improve agent quality, safety, and cost efficiency, developers need to determine where failures happen, what triggers unsafe effects, and which tasks consume the most budget, then optimize those tasks. In systems software, profiling answers similar questions by aggregating resource consumption and attributing it to responsible code paths to identify hotspots. Yet existing agent observability tools focus on per-execution debugging and tracing rather than cross-run, long term profiling, making these questions difficult to answer at scale. Agent observability needs profiling, not only debugging, but profiling agents is challenging: the responsible entities are task intent like diagnose authentication, compare branches rather than code paths, and lack stable identifiers for aggregation. We propose a semantic operation stack model that adapts profiling to agent trajectories. Uniform operations represent all activities, and operation stacks replace the runtime call stack, enabling hierarchical attribution at different granularities. We observe that an agent's task occupies a contiguous span and decomposes into subtasks, so we introduce recursive operation segmentation, which recursively splits trajectories at task boundaries. AgentPProf is a profiler that aggregates agent trajectories into pprof-compatible profiles, enabling flame graph visualization and analysis. AgentPProf reaches 0.764 $B^3$ F1 against human annotations on CodeTraceBench. On three problem-localization benchmarks, the profile raises MAP by up to 56%, demonstrating that it effectively attributes resources, locates problems, and helps optimize token cost at practical profiling cost. AgentPProf is available at https://github.com/eunomia-bpf/agentsight.

- **开发者真正关心的问题**：哪些类别的任务消耗最多 token 预算？故障集中在哪些工作流？哪些行为模式触发不安全的系统效应？这些问题难以靠人工检查或逐轨迹 LLM 评估在规模化场景下回答。
- **现有工具存在“调试/追踪”与“剖析”的缺口**：
  - 现有可观测性工具（LangSmith、Langfuse、Phoenix 等）将事件组织为单次执行的 span 树，适合诊断单次运行，但无法按任务意图或工作流阶段聚合。
  - 其他工具（Datadog LLM Observability、Laminar Signals 等）聚类输入或提取结构化信号，刻画的是输入分布（如“30% 用户问代码问题”），而非资源归因（如“review 任务消耗 40% token 预算”），因为请求级标签无法传播到下游工具调用和系统效应。
- **为何难以把传统剖析迁移到智能体**：传统剖析的负责实体是代码路径，函数名稳定、运行时调用嵌套提供归因层级。而智能体轨迹中：
  - 负责实体是**任务意图**（如 `diagnose authentication`、`compare branches`），两个表达相同意图的自然语言 prompt 没有公共字符串；
  - 轨迹**没有运行时调用栈层级**：prompt、工具调用、系统效应不按执行嵌套；一段 prompt 序列可能是一个任务也可能是多个任务，一个任务也可能是更大任务的一部分；
  - 缺乏用于聚合的**稳定标识符**。
- **核心论断**：智能体可观测性不仅需要调试，还需要剖析；剖析的方法论可迁移——把资源投影到负责实体、赋予稳定标识符、进行分层归因。

## 2. 方法论：核心思想、关键技术细节与算法流程

### 2.1 语义操作栈模型（Semantic Operation Stack Model）

- **统一操作（Operation）**：把所有活动（prompt、LLM 调用、工具调用、文件读写、GUI 点击、进程事件）表示为同一种带权记录，包含字符串字段（`project`、`agent`、`session`、`prompt_tag`、`kind`、`model`、`path`、`domain`、`status` 等）与可加性度量（token 数、时长、事件数）。仅有源内容、时间戳、可加性度量是必需的；显式工具/事件 ID、session、span 可选。
- **操作栈替代运行时调用栈**：用有序字段列表 `[f1, f2, ..., fk]` 把操作 `o` 投影为帧序列 `⟨o.f1, o.f2, ..., o.fk⟩`，帧序列相同的操作合并并求和权重。字段在**查询时**选择，而非由执行决定——改变字段即可按任务、session 或动作类型归因，无需重建数据。
- **视图（View）三元组**：`(φ, σ, w)`，其中 `φ` 为选择参与操作的谓词，`σ` 为栈函数，`w` 为非负权重函数。内置四种视图：tokens（LLM 调用按 token 加权）、time（所有计时操作按时长加权）、files（文件操作按事件数加权）、network（网络操作按事件数加权）。
- **三条设计需求**：
  - **R1 跨层投影**：把系统层消耗连接到意图层类别，通过 tag 继承（借助 AgentSight）让意图标签传播到其触发的系统效应。
  - **R2 稳定标识符**：从自然语言 prompt 中导出简短、可重复的标识符。
  - **R3 分层归因**：从数据而非执行嵌套构造归因层级。

### 2.2 递归操作分割（Recursive Operation Segmentation）

- **核心直觉**：一个任务占据轨迹的连续区间，并分解为更小的连续子任务，因此任务结构可建模为一组**嵌套的命名区间**，只需找到它们之间的**转移点**即可恢复。
- **形式化**：轨迹为有序步骤序列 `T = (t1, ..., tn)`；分割为命名区间集合 `S`，满足嵌套性（任意两区间不相交或一个包含另一个）、覆盖所有步骤、以会话级区间为根。
- **递归规则**：`Segment(I)` 在区间 `I` 内选择零个或多个转移点，将 `I` 划分为连续子区间；每个子区间获得一个**以动词开头的短名称**并递归分割；不选转移点则终止该分支。一个步骤的操作路径即包含它的区间的名称链（从会话根到最内层区间）；相同路径跨会话折叠。
- **示例**：一次 Git 部署执行被切分为 `build deployment system`，其内部再切出 `deploy branches` 与 `diagnose authentication`，后者中的步骤携带路径 `build deployment system > diagnose authentication`；相同名称在其他两次执行中重现，成本即折叠。
- **实现方式**：任何能找转移点并命名区间的实现（智能体、语言模型或统计规则）都可作为分割器。论文使用 Codex（GPT-5.6-sol-high），每条轨迹一条固定指令：读取轨迹（每步的 prompt、命令、输出摘要，无标签无分数）→ 在责任变化处发出标记 → 用 AgentPProf 检查并迭代更新 → 输出稀疏路径标记（如 `step 1: [deploy git server]`、`step 4: [deploy git server, diagnose SSH access]`），名称以动词开头、1–3 个词。稀疏标记因中间步骤继承前一路径而仍产生完整分割，且支持增量修订。
- **非 LLM 备选**：基于 NPMI 打分转移点，并用 k-means 校准无监督阈值。

### 2.3 剖析流水线（四阶段）

1. 把原始轨迹解析为操作；
2. 把轨迹分割为命名的嵌套区间（或应用映射规则）；
3. 在查询时把每个操作投影到选定的栈帧序列；
4. 折叠相同栈的操作并求和权重。

### 2.4 实现要点

- Rust CLI，约 9.8K LOC；读取 Codex 与 Claude Code 的本地 JSONL 历史文件及 AgentSight 记录；文件在执行期间增量写入，故可在智能体仍运行时构建剖析。
- 分割智能体读取可读轨迹摘要并写入区间标记到注释文件，可反复修订；CLI 校验标记嵌套且覆盖所有步骤后，输出标准 pprof protobuf profile，可直接被 `go tool pprof` 读取。
- 投影是确定性的：每个操作贡献语义路径与 LLM/工具证据，session 身份作为 pprof 标签而非可见帧，使相同语义前缀跨会话折叠。切换可加性度量只重放注释、改变栈宽。
- 已按字面记录的字（如 skill 调用）无需标注成本即成为栈层级；多智能体编排自动生效，因为子智能体操作继承外层智能体的语义路径。
- 对缺失/冲突链接采取 **fail-closed** 策略：不推断父节点，仅语义区间名从内容推断。
