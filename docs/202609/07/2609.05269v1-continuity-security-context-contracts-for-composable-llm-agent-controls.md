## 摘要
LLM智能体系统日益将来源追踪、授权、策略执行、协议适配器和执行控制相结合。然而，单独正确的安全机制并不一定能组合成端到端的安全系统：当操作跨越组件边界时，安全关键上下文可能被丢弃、放宽、重新绑定或重新解释。我们将这种失效模式识别为安全上下文不连续性，并引入CONTINUITY，一个用于智能体安全控制可验证组合的框架。CONTINUITY使用假设-保证契约为每个组件建模，并通过签名根授予、来源承诺、角色绑定转换收据、有界类型释放、转换见证和效果受限执行许可，在转换过程中携带经过身份验证的安全上下文。我们形式化了端到端后果完整性，要求每个实现的外部效果都必须有有效且最新的授权见证支持，该见证将主体、任务、来源、委派、策略状态、规范操作和最终性边界联系起来。我们实现了一个参考验证器和确定性跨层故障注入套件，涵盖四个应用领域的32个故障类别。在跨越128个故障域类别的2,560个参数化攻击实例中，完整的CONTINUITY配置没有产生任何有害外部效果，同时完成了所有700个良性任务并升级了所有200个模糊案例。这些结果表明，安全的智能体执行不仅需要健全的单独控制，还需要显式契约，以在完整的指令到效果路径上保持其保证。

## Abstract
LLM agent systems increasingly combine provenance tracking, authorization, policy enforcement, protocol adapters, and execution controls. However, individually correct security mechanisms do not necessarily compose into an end-to-end secure system: security-critical context may be dropped, widened, rebound, or reinterpreted as actions cross component boundaries. We identify this failure mode as security-context discontinuity and introduce CONTINUITY, a framework for verifiable composition of agent security controls.   CONTINUITY models each component with an assume-guarantee contract and carries authenticated security context across transitions using signed root grants, provenance commitments, role-bound transition receipts, bounded typed releases, transformation witnesses, and effect-bound execution permits. We formalize end-to-end consequence integrity, requiring every realized external effect to be backed by a valid and current authorization witness linking the principal, task, provenance, delegation, policy state, canonical action, and finality boundary.   We implement a reference verifier and deterministic cross-layer fault-injection suite covering 32 fault classes across four application domains. In 2,560 parameterized attack instances spanning 128 fault-domain classes, the full CONTINUITY configuration commits no harmful external effect, while completing all 700 benign tasks and escalating all 200 ambiguous cases. These results show that secure agent execution requires not only sound individual controls, but explicit contracts that preserve their guarantees across the complete instruction-to-effect path.

## 1. 核心问题与整体含义

- **研究背景**：LLM 智能体系统越来越多地组合多种安全控制机制（如来源追踪、任务范围授权、策略网关、协议适配器、效果绑定执行等）。这些机制在单独开发和测试时往往“看起来没问题”，但其组合却可能产生端到端的安全漏洞——例如某个环节丢弃来源标签、接受自声明权限根、扩大授权范围、在无有效转换认证的情况下更改字段值，或执行过期/重放的权限凭证。
- **核心问题**：作者将这类失效模式命名为 **“安全上下文不连续性”（security-context discontinuity）**，即安全相关的事实（授权来源、字段来源、策略状态等）在跨组件传递时被丢失、弱化、重新解释或重新绑定。
- **总体含义**：文章主张一种范式转变——安全保证不能只依赖单独的组件正确性，而必须通过**端到端、可验证的上下文字段传递契约**来确保从初始指令到最终外部效果的每一个环节都不出现上下文断裂。

## 2. 方法论：核心思想与技术细节

- **核心形式化目标——端到端后果完整性（ECI）**：每个已实现的外部效果 e，都必须存在一份完整的验证见证（witness）We，将具体效果连接到经过认证的链源（root grant）、主体（principal）、任务（task）、字段级来源（field-level provenance）、根授权、组件契约、当前策略、最终性接收器和一次性执行状态。
- **假设－保证（Assume–Guarantee）契约模型**：每个组件 \(C_i\) 建模为四元组 \((A_i, G_i, P_i, M_i)\)，其中：
  - \(A_i\)：输入假设；
  - \(G_i\)：输出保证；
  - \(P_i\)：必须保留的字段（fields）；
  - \(M_i\)：显式的转换关系（transformation relation）。
  - 安全组合要求：上游组件的保证能够满足下游组件的假设，且每次字段变更要么被保留（preserved），要么有独立可验证的关系见证（transformation witness）作为正当理由。
- **七条可验证充分条件（C1–C7）**：
  1. **C1：认证源（Authenticated origin）**——必须有受信入口、签名的根授予、受信签名者集合和字段级约束，避免"祖先不设防的链起点"；
  2. **C2：契约兼容性**——下游组件的每项假设必须由上游根授予或有效前驱的保证所满足；
  3. **C3：上下文连续性**——每个安全关键变更路径要么保留原值，要么由验证过的关系见证所证明；
  4. **C4：非放大（Non-amplification）**——授权与委派范围只能由显式认证的授权边扩大，未经发布的不可信数据要进入受保护字段必须有类型化发布（typed release）；
  5. **C5：规范动作绑定**——许可（permit）和最终接收器必须绑定相同的规范动作（含工具/服务器/清单标识、操作、资源、目标、参数、效果类别、数据类别）；
  6. **C6：最终性新鲜度**——执行前即时重检主体、受众、策略、撤销、过期、nonce 和幂等状态；
  7. **C7：完整调解（Complete mediation）**——效果等价类别中的每一条路径都必须经过兼容的最终性接收器。
- **关键机制清单**：
  - 签名根授予（signed root grant）——限制整体任务边界；
  - 角色绑定组件身份——组件密钥只能用于由其配置角色和契约授权的阶段；
  - RFC 6901 式 JSON Pointer 叶路径——语义字段级别的精确寻址和变更检测；
  - 有符号来源/上下文清单——绑定并校验字段来源；
  - 有界类型化发布（typed release）——不可信数据进入目标字段的单一来源、值和谓词约束；
  - 转换见证（transformation witness）——认证真实合法的语义转换（如别名→规范地址）；
  - 一次性最终性许可（one-shot allowed final permit）——绑定主体、动作、策略、撤销和重放状态。

## 6. 主要结论与发现

- **完整配置 CONNTINUITY 零有害效果**：2,560 个攻击实例均未产生有害外部效果，128 个故障-领域类别全部被覆盖，良性任务自动完成率 100%，模糊任务升级率 100%；
- **不完整配置显著失效**：最强的参考配置（Gateway + Finality）在 65.6% 的攻击实例中仍产生有害效果；Effect-bound permit 仅覆盖 24 个类别，ASR 为 81.3%；Pure gateway 的 Strategy 只覆盖 4 个类别。
- **受信任的语义变换可带内保持**：所有正常路径包含一个真正的安全相关变换（逻辑别名→规范地址），只有在目录见证和关系验证正确时才允许执行；
- **消融量化了不变量优先级**：缺失字段级来源 / 契约一致性 / 完整调解会各打开 24 个类别；缺失根认证打开 16 个；缺失发布验证打开 12 个。
- **关键系统含义**：单个局部合理的安全机制（如中间件、签名、策略网关或行为绑定许可）无法保证端到端安全——必须在每个界面处显式传播并重验证安全上下文。将规划保留在概率性和对抗性侧，外部后果则应让确定性、可验证的受信小控制平面来把关。

## 7. 优点

- 将“安全上下文不连续”作为一个单一、精心定义的问题类别来提出和归类（32 个故障类）。
- 将学术界熟悉的假设-保证思想应用到 LLM 代理安全的具体语义中，并明确给出可验证的条件。
- 通过一个轻量的参考实现，准确地演示了根授予、字段级来源、类型化发布、转换见证、角色绑定受信状态和最终性检查之间的相互作用。
- 评价以**确定性**方式同时覆盖“安全目标”与“效用目标”——良性任务正常完成，模糊任务在未获发原子时安全升级而不是默认拒绝。
- 在负例方面公开了完整配置和不完整配置的结果，以便清晰定位 ECI 结构和故障注入方法的贡献。
- 关注现实部署问题（过期、吊销、重放、幂等、策略轮换），而不仅仅是传统的模型提示分类。

## 8. 不足与局限

- **信任根本身是外部配置**：根授权的密钥、受信来源发布者（directory）、来源提取逻辑等均被视为 TCB 的一部分；任何受信链顶端的恶意配置或密钥泄露都会失去对应的保证。
- **不是语义正确性证明**：即使所有结构检查通过，受信来源仍可能输出错误的结构化事实（例如错误地提取发票金额），系统会忠实地保留并执行错误的结论。
- **上下文清单的完整性假设**：验证器验证清单摘要，但需要外部运行时保证清单确实覆盖模型所见的全部字节——这是未包含在系统内的委托信任假设。
- **转换语言“过窄”**：实现仅覆盖更丰富的别名解析和一个小的谓词注册表，而实际生产系统包含翻译、映射、聚合等多类语义转换——这些更丰富的谓词需要额外设计，且在通用关系语言中寻求**可判定性、可靠性和可审计性**是实现面临的实际挑战。
- **无形式验证实现**：正式证明适用于抽象模型，Python 原型依赖回归测试，未做机器验证、恒定时间或硬化实现。
- **合成基准不推论真实世界**：32 个故障模板并非穷举，参数化变体不是从真实攻击分布抽样得来的。零失败率不代表对未知类别的攻击概率为零。
- **简化执行者语义**：最终性世界、一次性记录存储、幂等性均为内存原子存储模型；真实分布是并发、不完全一致、幂等和失败语义较弱的服务。
- **不阻止静默泄露**：不会删除自定义的信息外传通道、隐蔽的时间/资源名称通道，或由 LLM 生成的纯文本的外传文本。文内仍承认辅助信息通道属于遗留风险。
- **没有处理人的/语义的失误**：即使所有机制都正确执行，用户仍拥有对一个不好设计或有害的根授权的合法授权；系统验证授权关系的连接性，但并非评判授权任务的明智性与合法性。
