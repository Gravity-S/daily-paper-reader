## 摘要
自主LLM智能体日益代表用户行事：它们持有凭证、调用工具和服务，并生成进一步代表用户行事的子智能体。这使一个长期存在的分布式系统问题——谁被授权做什么、依据谁的权威——成为一个紧迫且在很大程度上尚未解决的问题，因为驱动每个智能体的组件是一个可能被对手劫持的语言模型。我们认为，智能体安全必须在不信任模型假设下进行评估：一个正确的系统是指，即使一个完全被提示注入的智能体也不能超出显式委托给它的权限。针对这一标准，我们做出三项贡献。首先，我们提出了一个以四种对手为中心的多智能体委托威胁模型——混淆代理、令牌窃取与重放、提示注入特权升级以及被攻陷的子智能体——并推导出一个受治理的智能体系统必须满足的八项安全要求。其次，我们证明这一差距是真实存在的：一个模拟常见实践（广泛承载凭证、模型内部授权门控）的默认智能体运行时无法抵御所有四种威胁，而且在四种广泛使用的框架中——LangGraph、CrewAI、AutoGen和模型上下文协议（MCP）授权模型——三种没有提供内置隔离，一种仅提供部分隔离；现有的标准单独都没有覆盖这一要求集。第三，我们实现并对抗性地评估了一个弥补差距的授权代理。它阻挡了所有四种威胁；它抵御了对其设计的11次直接攻击，并拒绝了200,000个伪造令牌中的全部；它将一个被攻陷的子智能体限制在其委托任务范围内（在2,000个随机化场景中，平均可达动作数为1.5，而承载委托下为全部8,100个）；并且它以微秒级成本执行（每次决策约2.6微秒），相对于模型推理而言可忽略不计。这些原则也在VotalAI的LLM Shield中生产环境中实现。

## Abstract
Autonomous LLM agents increasingly act on a user's behalf: they hold credentials, call tools and services, and spawn sub-agents that act further on their behalf. This turns a long-standing distributed-systems question -- who is authorized to do what, on whose authority -- into an urgent and largely unsolved problem, because the component driving each agent is a language model an adversary can hijack. We argue that agent security must be evaluated under an untrusted-model assumption: a correct system is one in which a fully prompt-injected agent still cannot exceed the authority explicitly delegated to it. Against this standard we make three contributions. First, we give a threat model for multi-agent delegation centered on four adversaries -- confused deputy, token theft and replay, prompt-injection privilege escalation, and compromised sub-agents -- and derive eight security requirements a governed agent system must meet. Second, we show the gap is real: a default agent runtime modeling common practice (broad bearer credentials, authorization gated inside the model) fails all four threats, and across four widely used frameworks -- LangGraph, CrewAI, AutoGen, and the Model Context Protocol (MCP) authorization model -- three provide no built-in confinement and one only partial; no existing standard alone covers the requirement set. Third, we implement and adversarially evaluate an authorization broker that closes the gap. It blocks all four threats; it resists 11 direct attacks on its design and accepts 0 of 200,000 forged tokens; it confines a compromised sub-agent to its delegated task (a mean of 1.5 reachable actions versus all 8,100 under bearer delegation, across 2,000 randomized scenarios); and it enforces at microsecond cost (about 2.6 microseconds per decision), negligible against model inference. These principles are also realized in production in VotalAI's LLM Shield.

## 一、核心问题与整体含义（研究动机与背景）
- **核心问题**：多智能体 LLM 系统中，智能体代表用户持有凭证、调用工具并派生子智能体，形成“委托链”。由于驱动智能体的语言模型可能被提示注入（直接/间接）完全劫持，传统分布式系统中的授权问题（谁被授权做什么、依据谁的权威）在智能体场景下面临新的、尚未解决的安全挑战。
- **关键立场**：作者提出“不可信模型假设”（Untrusted-model property）——一个系统只有在“模型输出完全被攻击者控制（被完全提示注入）的智能体仍无法超出显式委托权限”时才算治理良好。模型是系统中最易受攻击的部分，因此必须被视为不可信；任何依赖模型不被劫持的安全方案都不是真正的安全。
- **研究现状与缺口**：现有主流智能体框架（LangGraph、CrewAI、AutoGen 等）默认将模型当作可信组件——为智能体颁发宽泛的长期有效承载令牌、委托时不对子智能体缩小权限范围、将敏感操作的授权门控交给模型自身推理——而这些框架在默认配置下几乎没有内置授权或委托隔离能力，MCP 授权模型仅提供部分覆盖。现有身份与授权标准（OAuth、OIDC、SPIFFE、Macaroons 等）单独均无法完整覆盖多智能体委托场景下的全部安全要求。

## 二、方法论：核心思想、关键技术细节与流程
1. **威胁模型**：
   - 定义了四种核心对手（Adversaries）：
     - T1 混淆代理（Confused Deputy）：持有合法授权的智能体被注入内容操纵，将授权用于攻击者目的。
     - T2 令牌窃取/重放（Token Theft/Replay）：承载凭证被窃取后从不同上下文重放。
     - T3 提示注入特权升级（Prompt-injection Privilege Escalation）：注入内容使智能体获取或行使超出任务所需权限。
     - T4 被攻陷的子智能体/权限过宽（Compromised Sub-agent）：子智能体或工具被攻破，因持有过宽/未衰减的委托权限导致破坏半径超过任务范围。
2. **安全目标与八项安全要求（R1–R8）**：
   - G1 被劫持智能体不能行使超出显式委托的权限；G2 每次委托只能缩小权限；G3 窃取凭证无法脱离原始工作负载使用；G4 可及时撤销；G5 每次特权操作可归属到委托链。
   - R1 委托链完整性（on-behalf-of provenance）；R2 最小权限衰减；R3 发送方绑定凭证；R4 短期签发；R5 密钥/秘密轮换；R6 撤销传播；R7 完整、防篡改审计；R8 与模型无关的强制执行（由基础设施 PEP 决策，绝不依赖模型）。
   - 其中 R8 是承重要求——若由模型门控权限，被劫持的模型就相当于授予了访问权。
3. **默认运行时基线实验**：实现一个典型的“默认运行时”——单一宽泛承载凭证传给主智能体后原样下传，动作是否允许由模型推理决定（无外部策略点）。结果显示其无法提供 R1–R8 中任何一项，四类威胁全部得逞。
4. **授权代理（Broker）设计与实现**：
   - 每个智能体通过 SPIFFE 风格工作负载身份（SVID）认证（R3/R5）。
   - 人类授权以能力令牌（capability token）为根，锚定于 OIDC 身份（R1）。
   - 每次委托跳转由代理进行 issuer 中介的令牌交换，铸造新令牌——为子任务衰减范围（R2）、绑定接收方 SVID（R3）、短生命周期（R4）；令牌绑定方才能继续向下委托。
   - 所有工具调用由代理/策略执行点（PEP）中介；代理独立于模型验证令牌并强制 caveat（R8），将委托链追加到防篡改日志（R7）。
   - 撤销使令牌失效并沿委托链传播（R6）。
   - 实现为约 160 行 Python（仅标准库），HMAC 签名令牌（macaroon/OAuth Token Exchange 风格）；伪造、移除 caveat、改绑主体等操作因缺少代理密钥而验证失败；caveat 仅可追加，权限只减不增。强制检查流程：签名验证 + 撤销检查 + 发送方约束检查 + caveat 求值，全部无模型调用。

## 六、主要结论与发现
- 默认智能体运行时（宽泛承载令牌 + 模型门控）在不可信模型假设下无法抵御任何一类核心威胁。
- 主流框架（LangGraph、CrewAI、AutoGen）默认未提供任何内置授权/委托隔离能力；MCP 仅提供部分覆盖。
- 现有身份与授权标准虽然提供了成熟原语，但没有任何单一标准能够覆盖所有八项要求，且原语未针对代理到代理委托场景组合。
- 通过“工作负载身份绑定 + 逐跳衰减令牌交换 + 外部 PEP 强制执行 + 防篡改审计”的授权代理组合，可以弥合这一差距：
  - 阻断全部四类威胁；
  - 抵御 11 类设计攻击，20 万个伪造令牌零接受；
  - 将受陷子智能体可达动作从环境全部的 8,100 个降至平均 1.5 个，且可达边界由任务决定、与部署规模无关；
  - 每次授权决策约 2.6 μs、令牌交换约 5.4 μs，相对模型推理开销可忽略。
- 内容过滤/模型侧护栏（如输入输出过滤器、guardrail models）是必要的补充层，但不能替代模型外部的权限范围治理——因为它们是概率性的且位于已被攻破的信任边界内部。
- 作者提出思想宣言：“当模型被劫持时，这个系统是否仍然安全？”应成为每个智能体部署的默认检验问题。

## 七、优点与亮点
- **思想定位清晰**：坚持“不可信模型属性”作为标准，不做“模型不会被骗”的假设，切中智能体安全要害。
- **问题-解决方案范式**：既展示具体漏洞（默认运行时失败 + 多框架差距），又实现并主动攻击防御方案，避免了纯分析或纯声称。
- **威胁模型与需求系统化严谨**：从四类对手推导八项需求，并与主流框架、九项标准逐一映射，定位缺口深入到标准层面而非停留在框架默认配置。
- **对抗评估较全面**：不仅验证“防住了四类威胁”，还包含针对代理本身设计的大量反制攻击测试与大规模 fuzz。
- **爆破半径指标设计合理**：用“绝对可达动作数 + 环境规模无关性”作为核心不变式，比单一百分比更有说服力。
- **性能开销证据清晰**：给出 µs 级代价并强调相对模型推理可忽略，兼顾安全与工程可行性。
- **外部一致性**：与同期独立研究 [33] 对 LangChain/LangGraph 默认缺口的结论互相印证，增强可信度。
- **工程落地与学术界参考实现分离**：说明参考实现未发布，生产系统信息界限清晰，有益于独立复现与验证。

## 八、不足与局限
- **框架评估方式不均匀**：LangGraph 为执行验证，CrewAI/AutoGen 仅为代码能力检查，MCP 为规范分析；检查深度不一致，“Y”标记的同质性值得商榷。
- **基准实现与框架集成缺失**：Broker 未真正嵌入被测框架；作者自述与真实模型配合的端到端评估留作未来工作，当前评估更接近“层验证”而非“全栈验证”。
- **版本时效性**：各框架/规范的具体版本（尤其 MCP 授权规范 2026-07-28）变化较快，未来版本可能引入新的内置保护使部分结论过时。
- **简化抽象风险**：Broker 强制的是抽象动作模型（工具/资源元组），生产 PEP 必须将现实工具调用正确映射到此模型，映射不当会造成误判或绕过。
