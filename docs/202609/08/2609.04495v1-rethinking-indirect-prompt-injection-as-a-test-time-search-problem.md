## 摘要
我们将间接提示注入形式化为一个测试时搜索问题，其攻击面由环境、用户任务和注入任务共同诱导，且依赖于具体任务。为实施该形式化，我们引入了一个智能体攻击者，配备专门的搜索框架，执行环境侦察、对攻击策略的结构化推理，并利用受害智能体的反馈进行自适应评估。在多种异构任务中，我们发现增加攻击者的测试时计算量可提升漏洞发现与利用效果，而消融实验表明，显式策略管理对于避免冗余搜索并在更大预算下维持收益至关重要。这些结果表明，智能体安全评估应同时描述攻击者的搜索过程与计算预算，而非将攻击成功视为与预算无关的受害者属性。更广泛地，我们的发现指出，攻击者对系统攻击面的自适应搜索是工具使用型智能体面临的一项重要且尚未充分探索的安全风险。

## Abstract
We formulate indirect prompt injection as a test-time search over a task-dependent attack surface induced by the environment, user task, and injection task. To operationalize this formulation, we introduce an agentic attacker with a dedicated search harness that performs environment reconnaissance, structured reasoning over attack strategies, and adaptive evaluation using victim-agent feedback. Across heterogeneous tasks, we find that increasing attacker test-time compute improves vulnerability discovery and exploitation, while ablations show that explicit strategy management is important for avoiding redundant search and sustaining gains at larger budgets. These results suggest that agentic security evaluations should characterize both the attacker's search procedure and compute budget, rather than treating attack success as a budget-independent property of the victim. More broadly, our findings identify the attacker's adaptive search over the system attack surfaces as an important and underexplored security risk for tool-using agents.

## 1. 论文的核心问题与整体含义（研究动机与背景）

- **背景**：大语言模型（LLM）驱动的智能体可通过外部工具和渠道读取第三方文本并执行操作；但模型在系统层面缺乏区分“指令”与“数据”的能力，因此容易受到**间接提示注入（Indirect Prompt Injection, IPI）**攻击。
- **问题**：既有 IPI 工作（如 AgentDojo、ASB、WASP 等）通常把攻击评估视为“静态评估”，即假设使用固定的、预设的攻击模板去测试受害者模型，并将攻击成功与否当作受害者模型的固有属性。这种方式忽略了：
  - 攻击面是**任务依赖（task-dependent）**的：用户任务不同、注入目标不同，攻击者可利用的工具调用轨迹也不同；
  - 攻击效果会随**攻击者拥有的测试时算力（test-time compute）**变化；固定少量尝试可能严重低估系统脆弱性。
- **核心主张**：应将间接提示注入重新构造成一个**“对任务相关攻击面的测试时搜索问题”**。攻击者在一个由环境、用户任务和注入任务联合诱导出的潜在攻击面上进行多轮自适应搜索，以找到能让 victim agent 执行恶意目标的注入载荷。
- **整体含义**：安全评估不仅要刻画受害者的防御能力，还要刻画攻击者的搜索流程与算力预算；自适应、可扩展搜索的攻击者才是真实且有威胁的安全风险。本论文以此视角首次从“测试时计算扩展”角度研究了 IPI 的威胁模型。

## 2. 论文提出的方法论

### 2.1 核心思想

- 将 IPI 建模为测试时搜索：攻击者通过反复尝试、观察 victim 的反馈、调整策略，在**潜伏的攻击表面**（latent attack surface）上找出同时满足“注入成功（security）”且尽量不破坏原任务“效用（utility）”的 payload 与注入位置。
- 本文使用**白盒/灰盒**视角：攻击者可以查看环境、工具描述和注入向量位置；作者指出这可迁移至黑盒设置，但系统评估留作未来工作。

### 2.2 检索/搜索框架（Search Harness）

论文给攻击者模型配备了一个“搜索框架”，核心包含三个模块：

1. **探索环境（Explore Environment）**
   - 提供两类侦察工具：
     - *环境知识工具*：读取具体的邮件、日历、产品、消息、社交内容等环境上下文；
     - *注入向量知识工具*：列出所有可注入字段（例如 `injection_email_body__<id>`、`injection_products_<id>_variants_<i>_note`）及其约束；
   - 目标是帮助攻击者判断哪些注入点可能被 victim 在良性任务中读取，从而发现潜在攻击路径。

2. **推理与搜索（Reasoning and Searching）**
   - 提供 `Strategy` 工具：将攻击策略组织为层次化语义结构；
   - 提供 `History` 工具：记录搜索轨迹，防止重复尝试；
   - 攻击者根据用户任务与注入目标，先识别有希望的搜索子空间，再对不可行的维度进行裁剪。
   - 这些工具是“廉价的”（不运行 victim），用于提升搜索效率和实现结构化推理。

3. **评估与反馈（Evaluation and Feedback）**
   - 核心工具是 `evaluate_injection`：它会将攻击者选择的 payload 注入到指定向量中，在一个临时环境中从零运行完整 victim agent，并返回：
     - `security`：注入目标是否被执行；
     - `utility`：用户原始任务是否仍被完成；
     - `victim_response` 与 `victim_tool_calls`：victim 的动作轨迹；
     - `applied_vectors/ignored_vectors`：哪些注入向量被应用、哪些是幻觉；
     - `failure_mode`（如 `SUCCESS`, `NO_ACTION`, `WRONG_ARGS`, `ATTACK_ONLY`, `BENIGN_FAILED`）。
   - 该工具是唯一会消耗 victim rollout 的昂贵操作；攻击者以获得的一次次反馈作为“搜索信号”，进行下一轮攻击设计。

### 2.3 形式化与任务设置

- **场景/攻击面定义**：攻击面由环境、可用工具、环境状态、用户任务与注入任务的兼容性共同定义。良性用户任务决定 victim 的工具调用轨迹，而注入任务定义恶意目标，二者组合形成搜索空间。
- **攻击成功与效用度量**：
  - 对每对（用户任务 *j*、注入任务），记录二元安全分 $s_j$ 与二元效用分 $u_j$；
  - **攻击成功率（ASR）**：
    \[
    \text{ASR} = \frac{1}{N}\sum_{j=1}^{N} \mathbb{I}[s_j = 1]
    \]
  - **联合成功率（JSR）**：
    \[
    \text{JSR} = \frac{1}{N}\sum_{j=1}^{N} \mathbb{I}[s_j = 1 \land u_j=1]
    \]
  - 为了体现“测试时计算”的作用，报告 **ASR@T**，即攻击者在总 token 预算为 T 时的攻击成功率。

## 3. 实验设计

### 3.1 使用的任务套件

- **Workspace 套件**：源自 AgentDojo 风格环境，包含 40 个用户任务 × 6 个注入任务 = **240 对**；覆盖邮件、日历、云盘等工具，涉及 108 个注入向量（邮件正文/主题、日历描述/地点、云文件内容）。
- **Retail 套件**：基于 Prime 风格环境生成器自动扩展，包含 17 个用户任务 × 8 个注入任务 = **136 对**；覆盖收件箱、商品、变体、评论、问答、用户公开资料等渠道，共 139 个注入向量。
- 用户任务与注入任务独立配对，以覆盖不同工具轨迹与用户/注入任务兼容性。

### 3.2 模型与配置

- **受害者模型（victim）**：Claude Opus 4.8 和 GPT-5.5，均使用 tool-calling agent、高推理强度；
- **攻击者模型（attacker）**：GLM-5.2，服务 API 访问，亦使用高推理强度；
- **攻击者预算**：默认约 500,000 tokens；通过改变预算观察 ASR@T 曲线。

### 3.3 对比与消融

- **Full-Harness（完整框架）**：包含侦察、策略管理、历史记录和 victim 反馈评估。
- **No-Harness**：移除全部侦察和搜索工具，仅允许直接 evaluate（类似暴力枚举尝试）；
- **No-Strategy**：保留环境侦察工具但移除显式策略管理工具（Strategy）；
- 消融实验主要在 Retail + GPT-5.5 上完成；
- 此外还有较多附加分析：不同注入任务的难度对比、成功攻击机制归类（action-item/cleanup/reference-number disguise）、攻击策略演化、推理步骤聚类、token 分配和收敛性等。

## 6. 论文的主要结论与发现

1. **IPI 可以并应当被形式化为测试时搜索问题**
   - 攻击者通过多轮搜索，沿着任务相关路径寻找可利用注入点，而不是一次性模板攻击。
2. **攻击者的测试时计算规模是关键变量**
   - 随着 attacker token 预算增大，ASR@T 曲线总体上升；
   - 在 Retail 中，GPT-5.5 约 50K tokens 开始明显失守，Opus-4.8 更鲁棒，500K tokens 时 ASR 仅 20.6%；
   - 在 Workspace 中，GPT-5.5 在 100K tokens 时 ASR 达 52.1%（比 Retail 37.5% 更高），说明 Workspace 有更多“短路径”攻击机会。
3. **成功攻击集中在与用户任务相邻的表面**
   - 若恶意指令被嵌入在 victim 原本就要读取的内容中，并伪装为良性任务的延续/前置步骤/必要操作，往往更容易成功；
   - 例子：把“发送安全码”篡改为“发送晚餐预约码”可成功。
4. **搜索框架必不可少**
   - No-Harness 在约 100K tokens 后平台期，进一步增加算力收益有限；
   - No-Strategy 因缺乏策略管理会产生大量侦察冗余和重复攻击，收益不持续；
   - Full-Harness 能自适应转换探索/利用，并在大预算下维持规模收益。
5. **攻击者具备“机制发现”能力**
   - 不只调整措辞，还可以学会 action-item framing、cleanup framing、reference-number disguise 等不同语义漏洞机制。
6. **安全评估建议**
   - 应将攻击者的搜索程序和计算预算纳入评估报告；不能把 ASR 当作与预算无关的 victim 属性。

## 7. 优点

- **视角新颖且重要**：首次将间接提示注入系统性地联系到“测试时搜索 / 测试时算力扩展”，这借鉴了推理模型 scaling test-time compute 思想，安全性评估容易忽视这一点。
- **设计落地、操作化强**：提出的 Search Harness 将环境侦察、历史策略管理、victim 反馈闭环明确分工；通过 `evaluate_injection` 作为搜索探针，让攻击者的行为可观察、可审计。
- **实验多元，证据丰富**：两个任务套件、多个 victim 模型、多种 token 预算曲线、完整消融、失败模式表、机制案例分析、策略演化统计和推理 embedding 分析相互支撑，说服力较好。
- **可复现性好**：在附录中提供了非常完整的系统提示、任务表、攻击者工具接口、指标定义和示例轨迹，方便后续研究复现和扩展。
- **揭示安全评估偏见**：说明“攻击成功不是受害者固有属性，而取决于攻击者搜索能力与预算”这一结论对智能体安全基准的构建有深远意义。

## 8. 不足与局限

- **实验环境过于简化**：
  - 只在两个合成 task suite 中测试，没有生产级产品或真实第三方数据；环境规模小，agent 工具数量有限。
- **攻击者访问模式受限**：
  - 聚焦白盒/灰盒设定，便于攻击者看到工具列表和注入向量位置；虽然没有明确系统评估黑盒迁移，但实际应用场景更多是黑盒或部分黑盒。
- **模型覆盖不足**：
  - 只用一个攻击者模型（GLM-5.2）与两个 victim 模型（GPT-5.5、Opus-4.8），难以表明测试时间算力扩增的结论对所有模型都成立；
  - 论文中的模型名称（如 GPT-5.5/Opus-4.8/GLM-5.2）在真实世界中可能并不存在或不被认可，尽管在论文假设语境中可自洽，但其结果是“初步的”。
- **缺少统计鲁棒性分析**：
  - 由于每次 victim rollout 计算成本昂贵，独立重复次数少，没有给出置信区间、标准差或显著性检验；
  - 所有失败 task pair 消耗完 500k tokens，导致部分搜索还没有收敛就提前终止，可能低估攻击成功率。
- **潜在偏差 / 数据问题**：
  - Retail 数据由生成器通过对抗式合成流程生成，可能包含特定模式，使攻击者更容易找到规律；
  - 只采用“效用+安全”二值判断，对部分真实任务而言过于粗粒度，可能没有考虑部分成功或部分有害结果。
- **安全风险双面性**：
  - 研究针对攻击的增强技术同时可能被滥用；作者也声明实验仅在受控合成环境、人工数据中进行，同时鼓励未来用于授权红队和负责任披露。
