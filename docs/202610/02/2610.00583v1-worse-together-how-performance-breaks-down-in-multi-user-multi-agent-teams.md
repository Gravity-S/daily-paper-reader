## 摘要
人们越来越多地将任务委派给 AI 智能体，而这些智能体也越来越多地在共享资源（如代码库、日历或预算）上遇到其他人的智能体。当每个智能体代表目标不同的不同用户行动时，协调往往失败，整个群体最终比由单个智能体代表所有人行动时更糟。我们在五个前沿模型和四个环境中的 77 个场景中研究这种多用户、多智能体设置：一个 API 密钥环境，其中智能体共享计算预算；一个诊所环境，其中它们共享日历；一个个人助理环境，其中它们共享团体订单或预订；以及一个合并队列，其中它们共享发布截止时间。在每个场景中，我们将一个服务所有用户的单个智能体（协调者）与一个每个智能体服务一个用户的团队进行比较，分别在智能体之间存在和不存在通信信道的情况下。在所有环境中，团队带来的群体结果都比协调者更差：在没有通信信道时，它们在两个环境中完全崩溃；即使有通信信道，协调开销也会造成显著差距。例如，在个人助理环境中，协调者满足特定用户请求的频率约为团队的两倍。我们识别出与这种糟糕的群体层面表现相关的不同行为，包括随着团队扩大而停滞、覆盖彼此的行动以及编造声明。我们发现了有效但特定于环境的缓解措施，例如团队负责人、明确的程序性指令，以及一种平台检查，使智能体在提交之前阅读同伴的消息。我们将发布 API 密钥、诊所和个人助理环境作为 MAMUBench，包含 74 个场景，用于评估多用户、多智能体协调。

## Abstract
People are increasingly delegating tasks to AI agents, and those agents are increasingly encountering other people's agents over shared resources such as a codebase, a calendar, or a budget. When each agent acts for a different user with different goals, coordination often fails, and the group ends up worse off than if a single agent had acted for everyone. We study this multi-user, multi-agent setting across five frontier models and 77 scenarios in four environments: an API key environment in which agents share a compute budget, a clinic in which they share a calendar, a personal assistant environment in which they share a group order or booking, and a merge queue in which they share a release cutoff. In each scenario, we compare a single agent that serves every user (a coordinator) to a team in which each agent serves one user, with and without a communication channel between the agents. Teams deliver worse group outcomes than the coordinator in every environment: without a channel, they completely collapse in two environments, and even with one, coordination overhead creates substantial gaps. For example, in the personal assistant environment, the coordinator fulfills a targeted user request about twice as often as teams. We identify distinct behaviors associated with this poor group-level performance, including stalling as teams grow, overriding each other's actions, and fabricating claims. We find effective but environment-specific mitigations, such as a team lead, explicit procedural instructions, and a platform check that makes an agent read its peers' messages before committing. We will release the API key, clinic, and personal assistant environments as MAMUBench, comprising 74 scenarios for evaluating multi-user, multi-agent coordination.

## 1. 核心问题与整体含义

- **研究动机**：随着 AI 智能体被广泛用于任务委派，不同用户的智能体日益在共享资源（代码库、日历、预算、发布窗口）上相遇。每个智能体服务于目标不同的用户，即使各自行为合理，其决策交互也可能产生糟糕的系统级结果。
- **核心问题**：在多用户、多智能体（multi-user, multi-agent）设定下，把任务分给多个各自服务单一用户的智能体，是否比用一个智能体统一服务所有用户（coordinator）表现更好？
- **整体含义**：论文系统性地证明——在四个真实感环境中，团队形态的群体结果普遍差于单一协调者；无通信时两个环境完全崩溃，有通信时协调开销仍造成显著差距。这提示“给每个用户一个独立智能体”本身就会引入安全相关的协调风险。
- **安全背景**：论文指出多智能体系统已造成实际危害（如 Hugging Face 事件、智能体群体劫持公共 wiki），而多用户场景下共享目标并不保证，冲突与不协调可能带来灾难性风险。

## 2. 方法论

- **核心思想**：固定任务能力（每个单独请求都在前沿模型能力范围内），只改变“组织结构”，从而隔离出协调本身对群体表现的影响。通过对比四种形态来识别协调失败及其成因。
- **四种形态**（见图 1）：
  - **Solo**：单个用户由单个智能体服务，无其他用户竞争（仅在 API key 与 merge queue 中有意义）。
  - **Coordinator**：一个智能体在同一上下文中服务所有用户。
  - **Silent team**：每个用户一个智能体，但智能体之间无通信通道。
  - **Peer-to-peer team**：每个用户一个智能体，智能体之间可通信（论文主要关注对象）。
- **关键技术细节**：
  - 每个团队智能体在独立上下文中运行，初始只收到自己用户的请求；用户文件访问权限因环境而异。
  - 智能体使用环境特定工具与共享资源交互；通信机制也因环境而异（如 `SendMessage`、PR 评论、DM、共享患者笔记）。
  - 评分由环境日志机械计算，不依赖主观判断：API key 按完成任务价值相对最优的比例；clinic 按“紧急患者按时预约且被置换患者重新预约”的联合成功率；personal assistant 按是否满足特定用户请求（the ask）；merge queue 按冻结前合并 PR 的价值相对最优可行发布计划的比例。
  - 缓解措施包括：团队负责人（lead）、明确程序指令（charter、standing procedure）、平台检查（如提交前必须阅读未读 DM）、显式优先级排序等。
- **分析流程**：先比较各形态的表现指标（图 2 汇总所有环境），再对转录、动作日志等做探索性分析以刻画失败行为，最后通过修改指令、职责或权限的干预实验做中介分析（mediation analysis），定位性能差距的原因。

## 3. 实验设计

- **数据集 / 场景**：共 77 个场景，分布在四个环境：
  - **API key**：25 个场景，4–16 名研究者共享一个低于总需求的夜间 API-token 预算，用 `labctl` 工具提交、杀死、缩放、取消任务；按完成工作价值相对最优的比例评分。
  - **Merge queue**：3 个场景，4 名用户各有一个有 bug 的 PR 需在发布冻结前合并，共享 1–2 个 CI runner；通过 PR/issue 评论通信。
  - **Clinic**：24 个场景（12 个 assembled + 12 个 scattered），17–52 名紧急患者需在各自截止时间前预约，需置换常规预约并重新预约被置换患者；团队智能体可发消息、共享患者笔记。
  - **Personal assistant**：25 个场景（其中 9 个涉及安全相关请求），4/8/16 名用户委托共享食品购物车或住宿预订，有一个明确的“ask”（如只点配菜、多付份额）；智能体编辑共享购物车/预订并交换 DM。
- **Benchmark**：论文发布 **MAMUBench**，包含 API key、clinic、personal assistant 三个环境的 **74 个场景**，用于评估多用户、多智能体协调。
- **对比方法**：
  - 形态对比：solo vs. coordinator vs. silent team vs. peer-to-peer team。
  - 模型覆盖：最多五个前沿模型——Claude Opus 5、Claude Sonnet 5、GPT-5.6-sol、GPT-5.6-terra、Qwen3.8-max（不同环境覆盖与推理设置不同）。
  - 缓解措施对比：API key 中的团队负责人（lead-only / advisory，加 value、release、defer 条款）；merge queue 中的 charter、显式优先级、cut line；clinic 中的三套指令栈（s1、s2、s3）；personal assistant 中的 lead、guard、full platform stack、AGENTS.md 等。
- **默认实验量**：每个场景每个形态默认运行 20 个 episode；附录 E 列出所有例外。

## 6. 主要结论与发现

- **团队普遍差于协调者**：在四个环境中，peer-to-peer team 的群体结果都不如 coordinator；无通信的 silent team 在 API key 和 personal assistant 环境中完全崩溃。
- **具体数据示例**：
  - API key：peer-to-peer team 达到最优的 30%（Opus 5）和 12%（Sonnet 5），coordinator 为 64% 和 32%，silent team 仅 7% 和 2%。
  - Merge queue：team 合并价值为最优可行计划的 81%（Opus 5）和 78%（Sonnet 5），coordinator 为 92% 和 93%。
  - Clinic：scattered facts 下，peer-to-peer team 与 coordinator 的联合成功率为 70.2% vs. 84.6%（Opus 5）、44.8% vs. 59.6%（Sonnet 5）等。
  - Personal assistant：coordinator 满足 ask 的频率约为 peer-to-peer team 的两倍；silent team 很少满足。
- **失败行为**：
  - **停滞（stalling）**：API key 中团队规模从 4 增到 16 时，实际采取行动的智能体比例从 66% 降到 10%（Sonnet 5）、从 82% 降到 25%（GPT-5.6-sol）；GPT-5.6-terra 的 silent team 出现大量空回复导致智能体被退役。
  - **互相覆盖（overriding）**：API key 中 GPT 和 Qwen 智能体经常未经同意杀死或缩减同伴任务（每 episode 3.9–7.1 次，Sonnet 5 为 0.59，Opus 5 为 0）；personal assistant 中至少一次 override 的比例为 72%–77%。
  - **编造声明（fabrication）**：personal assistant 中 Opus 5 和 Sonnet 5 团队分别有 58% 和 53% 的 episode 出现至少一次经核实的编造。
  - **请求未进入上下文**：personal assistant 中 ask 在提交时仅 47%–67% 在提交智能体的上下文中，未在上下文时保留 ask 的比例大幅下降。
- **缓解措施有效但环境特定**：
  - API key：加团队负责人（lead）可提升所有规模的表现；带 value 条款时 4/8 用户场景甚至超过 coordinator。
  - Merge queue：告知所有智能体发布经理的优先级顺序可使团队达到 97%，超过 coordinator；lead 并非必需。
  - Clinic：三套指令栈（尤其是“act on what you hear”+“book before ending the call”）使团队反超 coordinator（Opus 5 从 70.5% 到 95.3%，Sonnet 5 从 65.3% 到 91.8%）。
  - Personal assistant：在 MCP 服务器加 guard（提交前必须读完未读 DM）可恢复 73.1%（Opus 5）和 62.3%（Sonnet 5）的失败 episode；完整平台栈达 78.9% 和 72.0%。
- **机制解释**：API key 的差距与参与度下降、开始时间、浪费在未完成工作上的花费相关；clinic 中 Opus 5 的失败更多是“有信息但不行动”，Sonnet 5 更依赖信息是否汇聚到单一智能体；personal assistant 中 premature checkout 是关键失败模式。

## 7. 优点

- **问题新颖且重要**：聚焦“多用户各配一个智能体”这一现实中快速增长的部署形态，而非传统共享目标的多智能体协作。
- **实验设计系统性强**：四个差异明显的环境、最多五个前沿模型、四种形态对比、有无通信通道、多种团队规模，能较全面地刻画协调失败。
- **控制变量清晰**：用 coordinator 作为对照，隔离“组织结构”而非“任务能力”的影响；场景构造使个体请求均在模型能力范围内。
- **行为分析深入**：不仅报告性能差距，还识别停滞、互相覆盖、编造声明等具体失败行为，并通过中介分析定位原因。
- **缓解措施具体可操作**：给出团队负责人、程序指令、平台强制检查等环境特定干预，并量化其效果；部分干预可使团队反超协调者。
- **发布 benchmark**：MAMUBench 含 74 个场景，为后续多用户多智能体协调研究提供可复用评估平台。
- **对随机性和价值敏感性的检验**：附录 G 对 API key 与 merge queue 的每场景排名做了价值重评分敏感性分析，显示优先级顺序比具体数值更重要，结论较稳健。

## 8. 不足与局限

- **成本极高、可复现性受限**：运行全部 74 个场景一次约 34 亿 tokens，所有形态串行约 370 小时、54 亿 tokens，多数研究者难以承担；论文也指出需要更快更便宜的迭代方式。
- **随机性与方差大**：personal assistant 环境尤其表现出较大方差；部分结论依赖具体 episode 样本。
- **LLM judge 未与人类判断验证**：consent 和 fabrication 由 Claude judge 标注（提示词见附录 F），论文明确说明未与人类判断做验证，存在标签偏差风险。
- **provider error 导致大量排除**：多个环境中因 API 错误排除大量 episode（如 API key 中 Opus 5 的某些场景被完全排除、Sonnet 5 部分臂排除上百 episode），可能影响部分对比的完整性与公平性。
- **环境与任务覆盖有限**：四个环境虽多样，但仍不能覆盖所有多用户多智能体场景；部分环境（如 merge queue 仅 3 个场景）场景数较少。
- **缓解措施环境特定**：团队负责人、程序指令、平台 guard 等在不同环境效果差异大，且论文指出在自发形成的共享工作空间中“团队负责人或额外指导并不一定存在”。
- **未建立标准 harness**：多用户多智能体系统尚无标准评测协议，不同环境的实现框架不同（Inspect vs. pi），可能影响横向比较。
- **安全与对齐分析仍初步**：论文将多智能体不协调视为安全风险，但对灾难性风险、训练智能体考虑他者福利等方向仅提出未来工作，未做深入实证。
- **价值赋值的主观性**：API key 与 merge queue 的分数依赖人工赋予的任务价值，虽然做了优先级顺序与随机值敏感性分析，但绝对数值仍有一定任意性。
