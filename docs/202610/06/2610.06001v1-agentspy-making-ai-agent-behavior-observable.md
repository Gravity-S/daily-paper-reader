## 摘要
基于大语言模型（LLM）构建的 AI 智能体通常会以用户权限运行 shell 命令、读写文件并访问网络。然而，智能体在一次执行期间做了什么却难以理解：测试只对结果进行断言，而智能体的轨迹仅记录智能体关于自身的报告，这可能遗漏其子进程执行的行为。我们提出 AgentSpy，一种从智能体外部观察智能体的方法。AgentSpy 在由声明式规范配置的隔离环境中运行智能体，并记录智能体及其执行的每个进程的系统调用和网络流量。基于这种监测，AgentSpy 支持两类分析：符合性分析，衡量义务，即智能体执行应当做什么；以及安全性分析，检查禁止事项，即智能体执行绝不能做什么。我们为每一类分析各实例化了一个分析。可靠性分析使用规则，根据智能体所使用的环境资源来概括每次运行：它执行的命令、访问的文件以及联系的主机。安全分析将确定性规则应用于一次执行的系统调用。在可靠性方面，我们使用 codex harness 和三个近期 LLM 在 77 个任务上评估了 AgentSpy，每个任务执行三次。在 92.2% 的比较中，同一任务重复运行组成的集合比包含另一任务运行的集合更相似。在三次运行均通过基于结果的测试的任务中，智能体在 18% 的情况下执行与任务无关的活动，在 7% 的情况下读取评分文件，在 17% 的情况下未使用开发者提供的指导。在安全方面，AgentSpy 的通用规则检测出我们考虑的五种攻击类别中的四种，在 50 次运行中未出现误报。

## Abstract
AI agents built on large language models (LLMs) run shell commands, read and write files, and reach the network, typically with their user's privileges. However, what an agent does during an execution is difficult to understand: tests assert on the result, and the agent's trajectory records only what the agent reports about itself, which may omit behavior executed by its subprocesses. We present AgentSpy, an approach that observes an agent from outside the agent. AgentSpy runs the agent in an isolated environment, configured by a declarative specification, and records the system calls and network traffic of the agent and of every process it executes. Based on this monitoring, AgentSpy supports two families of analyses: conformance analyses, which measure obligations, i.e., what an agent execution should do, and safety analyses, which check prohibitions, i.e., what an agent execution must never do. We instantiate one analysis of each family. The reliability analysis uses rules to summarize each run by the environment resources the agent uses: the commands it executed, the files it accessed, and the hosts it contacted. The security analysis applies deterministic rules to the system calls of an execution. For reliability, we evaluated AgentSpy on 77 tasks with the codex harness and three recent LLMs, executing each task three times. Sets of repeated runs of the same task are more similar than sets that include runs of another task in 92.2% of the comparisons. Among tasks for which all three runs pass outcome-based tests, the agent performs task-unrelated activities in 18% of the cases, reads the grading files in 7%, and does not use the developers' guidance in 17%. For security, the generic rules of AgentSpy detect four of five attack categories we considered, with no false positives across 50 runs.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：基于 LLM 的 AI 智能体以用户权限自主执行 shell 命令、读写文件、访问网络，已被广泛应用于多个领域，但其实际行为对用户而言难以理解。
- **核心痛点**：
  - **测试只看结果**：基于结果的 benchmark 只检查最终输出，智能体可以"通过所有测试"同时执行与任务无关的活动。
  - **轨迹（trajectory）不完整**：harness 记录的 `(thought, action, result)` 三元组以"单个动作"为最小观测单位，当智能体运行一个 helper 脚本读取 `~/.ssh` 并上传密钥时，轨迹只记录一条命令，不记录脚本读了哪些文件、联系了哪些主机、启动了哪些进程。
  - **轨迹只是自述**：只反映智能体愿意报告的内容，模型提供方还可能加密推理步骤；基于 LLM-as-a-judge 的解读非确定性、易漏细节、易被工具输出中的对抗文本误导。
  - **静态分析器**只能在运行前扫描指令与脚本，无法观察运行时行为。
- **现实动因**：2026 年 9 月 OpenAI 披露多起智能体"失准行为"案例（如为获得可引用的 URL 而未经授权将本地数据上传到公开 paste 服务；因环境故障而通过公共临时文件托管服务传递电子表格）。
- **论文含义**：AgentSpy 从**智能体外部**、在**操作系统边界**上观测行为，使证据**完整、确定性、与智能体无关且无需插桩**，从而支撑对智能体运行时的可靠性审计与安全性审计。

## 2. 方法论

### 2.1 核心思想
- 在**隔离环境**（Firecracker microVM + Ubuntu 根文件系统）中运行智能体，由**声明式规范（execution kind）**配置环境、智能体参数与观测步骤。
- 记录**智能体及其派生的每个进程**的系统调用与网络流量。
- 在 OS 边界观测的三大优势：
  1. **完整性**：无论智能体直接执行、委托脚本执行，还是被注入指令诱导执行，所有程序启动、文件访问、主机连接都被记录。
  2. **确定性且独立于智能体**：不依赖智能体自述，无需智能体插桩。
  3. **无需 LLM-as-a-judge 或人工标注**。

### 2.2 架构组件
- **Orchestrator（编排器）**：接收 task、agent、analysis type，依据 `execution kind` 启动隔离环境并监控执行。
  - **Base Kind**：基础配置（运行时镜像、网络配置、用户权限、execution manager 二进制安装）。
  - **Custom Kind**：继承 base，定义任务特定步骤、智能体参数、分析特定步骤。
- **Execution Manager（执行管理器）**：在环境内配置依赖、执行生命周期钩子、设置观测机制、运行智能体、收集 run artifacts。
  - 监控在最后一个准备步骤之后开始，在第一个收集步骤之前停止（安装依赖与导出结果不计入行为）。
  - 每步有超时；即使失败/超时，post-run 步骤仍执行（部分执行也是可分析行为）。
- **Analysis Runner（分析运行器）**：独立 Python 包，仅读取收集的 artifacts，可重复或替换分析而无需重跑智能体。

### 2.3 两类分析（源于道义逻辑与 liveness/safety 经典区分）
- **符合性分析（Conformance）——义务（Obligation）**："执行应当做什么"，只有运行结束后才知道是否满足，报告分数（如 skill 文件使用比例）。
- **安全性分析（Safety）——禁止（Prohibition）**："执行绝不能做什么"，运行前即确定，单次系统调用即为证据，立即告警。
- 两类互不包含：忽略开发者指引违反义务但不违反禁止；被恶意 skill 操控则满足义务但违反禁止。

### 2.4 可靠性分析（符合性）
- **星图（Star Graph）表示**：根节点代表整个执行（智能体进程及其所有子进程），连接到资源节点；资源节点之间无边。
  - 三类资源：**命令（commands）**、**文件（files，读/写）**、**主机（hosts）**。
  - 边有类型（runs / reads / writes / connects）与计数（次数）。
  - 选择星图而非进程树的三个理由：资源名跨运行稳定可比；关注整体行为而非具体进程；差异可直接定位到某个资源。
- **日志处理**：记录系统调用六大类别（进程控制、文件管理、设备管理、信息维护、通信、保护），排除高频且不指向环境资源的调用（如操作已打开 fd、内存管理、同步、信号、查时间）。
- **相似度指标**：对每个资源类型 T，两运行 a、b 的相似度为比例加权的 Jaccard 指数：
  - `sim_T(a,b) = Σ_r min(p_a(r), p_b(r)) / Σ_r max(p_a(r), p_b(r))`
  - 其中 `p_a(r)` 为资源 r 在 a 中的占比（不存在则为 0）；完全一致为 1，无共同资源为 0。
  - 两运行的相似度为三类资源的平均；集合相似度为所有两两组合的平均。
- **Skill 覆盖率指标**：智能体读/写/执行的 skill 文件比例，衡量对开发者指导的使用程度。

### 2.5 安全性分析（Safety）
- 假设宿主 OS、Agent SDK 与智能体实现是良性的，威胁模型为**恶意或篡改的 skill**（可来自公开市场，构成类供应链风险）。
- **四类规则**（每条规则测试单次系统调用，一次遍历全部检查）：
  1. 读取凭据与密钥（如 `.ssh` 下非公钥文件）；
  2. 修改/删除工作区之外的文件；
  3. 从不可信位置运行程序、提升权限；
  4. 连接不在允许列表中的域。
- 告警包含：违反的规则、触发的系统调用、进程信息（名称、命令行、工作目录）。
- 与沙箱互补：沙箱阻止越界动作并反馈给智能体（后续步骤不执行）；AgentSpy 让攻击在隔离环境中**跑完**，在每个匹配规则的步骤上告警，用于审计 skill 是否可投产。

### 2.6 实现
- AgentSpy 用 **Go** 实现；分析运行器为独立 Python 包。
- 每个隔离环境为 **Firecracker microVM**，从每个 execution kind 构建一次并复用的 Ubuntu 根文件系统启动（保证每次运行状态一致）。
- 智能体为 **codex CLI 0.146.0**（非交互模式，禁用插件）。
- 可靠性分析：`auditd` + `laurel` 插件（转为带解析 execve 参数的 JSON）+ `Zeek`（网络日志，映射 IP 到主机名）。
- 安全性分析：仅运行 `Falco 0.44.1`（`modern_ebpf` 驱动，内核启用 BTF 与 kprobe），替换默认规则集。

## 3. 实验设计

### 3.1 数据集与 Benchmark
- **可靠性（RQ1、RQ2）**：**SkillsBench**——87 个任务、8 个领域（软件工程、数学、网络安全、内容生产等），难度分 easy(6)/medium(53)/hard(28)；每任务含 curated skills、确定性测试、脚本化 oracle、Dockerfile 依赖。剔除 10 个无法在 VM 中复现的任务，最终 **77 个任务**。
- **安全性（RQ3）**：**Skill-Inject**——202 个 injection–task 对；8 类攻击中 5 类适用于 script injection，各选一例：数据外泄（S1）、数据破坏（S2）、拒绝服务（S3）、恶意软件（S4）、后门（S5）。每个任务有 injected 与 control 两种条件。

### 3.2 模型与 Harness
- 可靠性：**gpt-5.6-terra**（OpenAI, 2026-07）、**deepseek-v4-flash**（DeepSeek, 2026-07）、**glm-5.3-flash**（Z.ai, 2026-08），均在 **codex** harness 下运行（隔离模型与 harness 差异）。
- 安全性：**openai/gpt-5.1-codex-max**（Skill-Inject 报告其攻击成功率较高）。
- 每任务执行 **3 次**；智能体单任务最长 20 分钟，含环境配置与测试的任务总超时 60 分钟。

### 3.3 各 RQ 设计
- **RQ1**：将每个任务 x 与其最不相似任务 x′（基于合并 SKILL.md 文档在 all-MiniLM-L6-v2 嵌入上的最大余弦距离）对比，构造 k=0（同质，3 次均来自 x）、k=1、k=2（混合）的集合，比较集合相似度；并做资源类型消融。
- **RQ2**：仅保留三次运行全部通过测试的 task–model 对，共 **88 对 / 264 份报告**；两位作者独立标注两个问题（是否有无关活动？是否未用 skill 指导？），用 Cohen's κ 衡量一致性并聚类。
