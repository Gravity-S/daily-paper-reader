# GTDD: Generative Test-Driven Development for AI Coding Agents with Adversarial Testing 

# Masahiro Kato ∗

# Mizuho-DL Financial Technology Co., Ltd. October 5, 2026 

Abstract 

Test-driven development gives AI coding agents executable requirements for im-plementing software. Because these agents can adapt their implementations to the examples they observe, passing a predetermined collection of tests can leave substantial parts of the intended behavior unimplemented. We propose Generative Test-Driven Development (GTDD), a formulation of test-driven development in which a separate testing agent generates new inputs after each candidate implementation is fixed, using a human-specified behavioral contract and the feedback from earlier rounds. A trusted evaluator checks these inputs, returns reduced counterexamples to the coding agent, and saves them for regression testing, so development continually confronts failures beyond the initial examples. We characterize the evidence that this process provides through a finite-population analysis of false acceptance under adaptive candidate selection. The resulting bounds quantify how test visibility and repeated feedback affect acceptance, and show that fresh random audits after candidate commitment control false acceptance across development rounds. In a paired experiment on a stateful key-value store, both policies that regenerated tests during development ended with lower mean failure rates than the policy whose tests were generated once by the same language model, and giving the tester the candidate’s source produced no detectable additional improvement. Further conditions requesting equal numbers of tests did not isolate any single feature of the policies as the source of this difference. GTDD combines this adaptive development feedback with established regression tests and an independent acceptance rule. 

# 1 Introduction 

Test-driven development (TDD) organizes software development around executable require-ments: developers write tests that describe the intended behavior, implement the corre-sponding functionality, and use those tests to check subsequent changes (Beck, 2002). This

As large language models (LLMs) take on code generation and repository repair, the connection between tests and successive implementation decisions becomes central to the reliability of the resulting software (Chen et al., 2021; Jimenez et al., 2024; Fakhoury et al., 2024). Existing systems already use generated tests to structure this interaction. CodeT evaluates candidate programs with generated tests, AlphaCodium uses them throughout an iterative coding process, and AgentCoder assigns programming and test design to separate agents (Chen et al., 2023; Ridnik et al., 2024; Huang et al., 2023). Guidance for Claude Code similarly describes a workflow in which one session writes tests and another writes the implementation (Anthropic, 2026). In an industrial integration setting, Krawczyk (2023) describes generative TDD based on historical input–output pairs that guide code generation and validate the generated mappings. These approaches make testing part of the development process itself, with test results shaping the next implementation. The same feedback that guides development also allows an agent to adapt to the tested examples without satisfying the full behavioral contract. A program may implement only the exercised cases or special-case their inputs, and an agent with broader access may attempt to change the tests. Additional benchmark tests have exposed incorrect programs that passed the original evaluation (Liu et al., 2023), while reward-optimization experiments have documented direct test subversion (Baker et al., 2025). This is an instance of the more general discrepancy between optimizing an observed objective and satisfying its intended purpose (Amodei et al., 2016; Skalse et al., 2022). Increasing the number of tests and generating new tests during development address different parts of the problem, because acceptance also depends on what the coding agent has learned about those tests. A development framework must therefore specify both how new failures reach the coder and what evidence justifies accepting the resulting implementation. 

# 1.1 Contribution 

We propose GTDD as a general formulation of test-driven development with a separate generative tester. A human specifies the behavioral contract, the input schema, and the testing budget, while the tester creates concrete cases after the coding agent commits each candidate. The evaluator obtains expected responses from a trusted reference implementation and returns a controlled number of reduced failures to guide the next coding round. Saving generated cases and their reductions makes each discovered failure a regression test for later candidates. The formulation specifies what each agent may read and assigns independent random audits to the acceptance decision. Our theoretical analysis bounds the probability of accepting a candidate whose failure rate exceeds a prescribed tolerance on a fixed finite population. For a candidate class that can realize arbitrary casewise losses, we obtain the exact number of visible tests required for a uniform guarantee. For a hidden test set used repeatedly, we apply the description-length argument of Dwork et al. (2015a) to the possible feedback histories and give an explicit adaptive construction with a lower bound on its success probability. We also establish conditions under which generated tests support a sampling guarantee and derive fresh-2audit bounds for adaptive candidates. The acceptance analysis distinguishes simultaneous conclusions about individual requirement families from acceptance of the repository as a whole, and extends repository acceptance to an unbounded sequence of development rounds through a summable error allocation. We evaluate development feedback in a paired experiment on a stateful key-value store using the same language model as coder and tester. Both policies that generated new tests in each repair round ended with lower mean failure rates than the policy that generated tests once before development, which also requested fewer traces. The difference is concentrated in a few blocks, although the median difference is negative as well and the sign test detects it. Four further conditions that request equal numbers of traces produce intermediate rates with no detectable difference between adjacent conditions, so the study does not attribute the advantage to regeneration, to the number of traces, or to access to earlier counterexamples alone. Testers with and without source access showed no detectable difference, and neither dynamic policy had a detectable advantage over the property-based baseline drawn from the evaluation distribution. Applied to the recorded candidates, a fresh audit gives few expected acceptances, in line with their failure rates. GTDD brings together practices already represented in generative TDD and multi-agent coding systems, and gives their interaction an explicit statistical account. Whereas the generative TDD of Krawczyk (2023) validates generated code against historical input– output pairs, GTDD generates new inputs after each candidate is committed and separates this development feedback from the evidence used for acceptance. Its contribution is the organization of candidate commitment, testing information, counterexample feedback, and acceptance within one development process. Existing tests remain useful as executable examples and regression checks, while generated cases extend the feedback available during development. This combination is particularly relevant to applications with natural-language or speech input, such as telephone agents, where scenario generation and evaluation of acceptable behavior require separate design decisions. Section 3.5 describes how the protocol accommodates these applications. 

# 1.2 Related Work 

GTDD connects automated test generation with adaptive evaluation. The relevant dis-tinction among prior approaches is the role assigned to tests: specifying behavior, guiding implementation, or supporting an acceptance decision. 

Test generation and counterexample-guided development. Property-based testing generates structured inputs from a specification (Claessen & Hughes, 2000), while directed testing and symbolic execution search program behavior more systematically (Godefroid et al., 2005; Cadar et al., 2008). Language models have also been used to extend search-based generation and to fuzz deep-learning libraries (Lemieux et al., 2023; Deng et al., 2023). Counterexample-guided inductive synthesis provides the underlying iterative structure: a verifier finds an input on which a candidate fails, and that input constrains the next candidate (Solar-Lezama et al., 2006; Solar-Lezama, 2008). Delta debugging makes such feedback easier to use by simplifying a failing input while preserving the failure (Zeller & Hildebrandt, 2002). 3GTDD combines this structure with a generative tester and specifies a statistical acceptance rule when verification proceeds through sampled cases. 

Generated tests in AI coding. CodeT uses agreement with generated tests to select candidate programs, and AlphaCodium incorporates those tests into iterative repair (Chen et al., 2023; Ridnik et al., 2024). Test-driven interactive generation uses tests to clarify user intent (Fakhoury et al., 2024), and AgentCoder separates the programming, test-design, and test-execution roles (Huang et al., 2023). Class-level test-driven generation implements interdependent methods under method-level public tests with execution feedback and a bounded number of repairs (Liang et al., 2026b). CodeHacker generates adversarial inputs for a candidate and computes their expected outputs with a reference solution (Shi et al., 2026), and AdverTest alternates between test generation and mutant generation to expose weaknesses in the tests (Chang et al., 2026). Together with the industrial use of generative TDD described by Krawczyk (2023), these systems establish a substantial basis for generative testing. Menet et al. (2026) give a probabilistic account of the two main uses of an execution environment, selecting among generated programs and conditioning generation on feedback, and show that the ambiguity of the task description limits what feedback-conditioned generation can achieve. Their analysis concerns how efficiently generation reaches a correct program, whereas ours concerns the evidence that sampled tests provide about a committed candidate. We organize their shared development structure around explicit candidate commitment and feedback rules, then analyze the evidence available for accepting an adaptive candidate. 

Correctness and test-based objectives. Benchmarks such as SWE-bench evaluate repository repair, while SWE-bench Verified improves the alignment between issues and their evaluation tests through human review (Jimenez et al., 2024; Chowdhury et al., 2024). EvalPlus strengthens tests for generated code, and LiveCodeBench addresses contamination through temporally collected tasks (Liu et al., 2023; Jain et al., 2025). Our setting concerns a further source of dependence: the candidate learns from tests during its own development. The distinction between an observed objective and intended behavior is central to work on reward gaming (Amodei et al., 2016; Skalse et al., 2022), and the coding experiments of Baker et al. (2025) give concrete examples of test subversion. Paired interventions that change only the expected outputs of visible tests measure how far generated programs follow the rules those tests express, and the extent varies widely across models (Liang et al., 2026a). We describe test passing, population accuracy, and protected-file modification attempts as separate observable outcomes so that a correctness error is not treated as evidence of intent. 

Adaptive evaluation. Adaptive data analysis explains how repeated feedback can change the validity of conclusions based on a fixed evaluation sample (Dwork et al., 2015a; Russo & Zou, 2016). Our bound for repeated testing instantiates the description-length argument in Section 2.3 of the full version of Dwork et al. (2015a): count the possible histories and combine that count with an exact finite-population bound for each fixed candidate. Controlled feedback can also permit valid reuse, as demonstrated by the reusable holdout (Dwork et al., 2015b). Related concerns arise in adversarial evaluation, where an adaptive attack changes the interpretation of performance on a fixed collection of adversarial examples (Madry et al., 42018; Athalye et al., 2018; Tram` er et al., 2020). In GTDD, fresh sampling after candidate commitment supplies an acceptance sample whose conditional distribution is known despite earlier development feedback. 

Sequential inference. Sequential tests and time-uniform inference provide error control when the stopping time depends on observed results (Wald, 1945; Ville, 1939; Howard et al., 2021). The literature on testing by betting and safe inference develops this principle through nonnegative evidence processes (Shafer, 2021; Gr¨ unwald et al., 2024; Ramdas et al., 2023). We use these tools with an explicit hypothesis about the candidate under evaluation. Aprocess for one fixed implementation supports sequential inspection of that implementation, whereas a product across different implementations tests a statement about the sequence. This distinction determines which evidence can support the current acceptance decision. 

# 2 Problem Setup 

We model development as an adaptive sequence of candidate implementations evaluated against a behavioral contract. A fixed population of test cases defines the accuracy target, and the information supplied to each agent determines how later candidates can depend on earlier tests.

# 3 Generative Test-Driven Development 

GTDD places a separate testing agent inside the development cycle so that each committed implementation faces newly generated inputs. The contract and evaluation rules stay fixed, while the tester uses permitted feedback to search for failures that inform the next coding round. The protocol specifies this interaction independently of the rule used to accept an implementation.

# 3.2 Development Policies 

A development condition specifies how tests are generated and which failures are returned. These choices determine the information available for the next repair while leaving the acceptance rule separately configurable. 

Test generation. The protocol supports public examples alone, fixed tests generated from the specification, and tests generated in each round. Property-based generators and LLMs can supply either fixed or newly generated inputs. In a visible condition, the tests and expected responses are protected files inside the repository, whereas a hidden condition keeps them outside the coder’s access. Dynamic LLM testing additionally specifies whether the tester may inspect the source. We call the tester adversarial because its objective is to propose 9valid inputs on which the committed candidate disagrees with the reference implementation, using the information in It, the source when the condition permits it, and a fixed number of traces per request. Its success is the number of such failures it finds, and it has no access to audit samples or population results, so adversarial testing shapes development feedback but not the evidence for acceptance. 

Feedback selection. The standard rule prioritizes diversity across requirement families and failure mechanisms before selecting shorter traces. The compact-failure rule prioritizes short traces with few distinct operations and then families already reported. This second rule concentrates feedback on compact failures and allows a controlled comparison of how counterexample selection affects repair. Both rules act on the same observed development failures without access to audit allocations or population outcomes. Appendix B specifies their deterministic ordering and reduction budgets. 

Development outcomes. Discovery counts valid nonduplicate failures on the current candidate, with invalid and duplicate proposals kept in the denominator. Repair measures the next candidate’s performance on the reported counterexamples, while equation (9) measures improvement on the same previously unknown population cases. A regression occurs when a later candidate fails a saved test that it previously passed. Reporting these outcomes separately reveals whether a change in the final risk comes from discovering different failures, repairing the reported inputs, or preserving earlier behavior. Appendix C states elementary properties of these outcomes and of the information available to the tester. A comparison of development policies keeps the coding budget and acceptance rule fixed. The generation budget and repeated execution costs also belong to the specification of each policy, since an initial collection of tests incurs both generation cost and re-execution cost in later rounds. 

# 3.3 Acceptance Rules 

The acceptance rule states which evidence is sufficient to accept the committed candidate. Every rule requires an intact snapshot and passing public tests. Public screening stops at that criterion, and a regression-based rule additionally requires every saved development test to pass. GTDD uses a fresh audit of every requirement family to control false acceptance. Acondition may also require the regression tests to pass, and this additional requirement can only reduce the probability of accepting an inaccurate candidate. With a positive risk tolerance, an audit-only rule can accept a candidate that fails a known development case, so the choice to require regression tests is part of the acceptance specification. Comparisons between acceptance rules keep this choice and the development feedback fixed. The coder receives only the aggregate acceptance decision. Sampled inputs and family-specific results remain private. A trajectory can follow a prescribed stopping policy, including stopping at its first acceptance or continuing for a specified number of rounds. The upper bounds in Section 4 control the event that at least one accepted candidate exceeds a family tolerance during the evaluated trajectory. 10 3.4 Integration with Existing Tests 

Existing tests provide the starting point for GTDD by expressing the contract through concrete examples and protecting behavior that must remain correct. Re-executing them gives every candidate an inexpensive initial check, while generated tests extend the range of failures available for development feedback. The combined procedure keeps the initial tests, adds valid generated traces after each commitment, and saves the counterexamples reported to the coder. By equation (6), a failure found through generation becomes a fixed regression test for subsequent candidates. A strong property-based generator can also supply the initial tests when the input schema captures the relevant behavior. In the experiment of Section 6, the property-based baseline and the dynamic policies had no detectable difference in final failure rate, which makes this baseline an important part of the comparison. Acceptance draws a fresh sample after commitment from the population fixed before development. The sample size is determined before the draw, and individual audit cases remain outside the development process. This division gives examples and regression tests a stable role while assigning error control over the population to a known sampling rule. 

# 3.5 Applications 

The balance between existing tests and generated tests depends on how inputs can be produced and how correct behavior can be evaluated. GTDD makes both choices explicit, whether inputs are structured operation traces or natural-language interactions. 

Structured inputs. For a key-value store, parser, or formally specified interface, an operation schema describes valid inputs and a reference implementation supplies expected outputs. A bounded collection of traces then defines a finite population on which committed candidates have fixed losses. This setting directly supports the post-commit sampling assumption used in the acceptance analysis. 

Language and speech. A telephone agent encounters dialogue patterns such as inter-ruptions and topic changes, while the consequences of an utterance depend on the agent’s dialogue state and tool calls. Generated scenarios can vary these patterns and target the flows exposed by the candidate implementation. For speech input, scenarios can also represent recognition errors, accents, and background noise. Existing scripted calls remain useful for requirements such as identity verification before an account change and transfer to a person on request. Generated dialogues complement these checks and become regression tests when they expose a failure. 

Evaluation criteria. Natural-language responses often admit several acceptable outcomes, so evaluation may use a rubric, a model-based judge, or human review instead of a reference implementation. The finite-population guarantees concern the loss assigned by the specified evaluator on the listed scenarios and require reproducible candidate and evaluator behavior. The validity of that criterion is a separate question about its agreement with the intended behavior. Fixing the evaluation procedure before development and keeping audit scenarios 11 private preserves the distinction between generating useful feedback and deciding whether the candidate meets the stated target. 

# 4 Theoretical Analysis 

We seek a frequentist bound on the probability of accepting an implementation whose failure rate exceeds the prescribed tolerance. The population and each committed candidate’s losses are fixed, while probability is taken over test sampling and any independent randomization in development. The analysis first relates false acceptance to sample size, then accounts for the information available when the candidate is chosen. This establishes which guarantees follow from known tests, repeated feedback, and newly sampled tests, and yields a sequential acceptance rule for GTDD. Fix an issue and one requirement family, write U = {z1, . . . , z N } for its population of size N , and let R(f ) be the family risk in equation (2) with tolerance ρ ∈ (0 , 1). We call a candidate bad when R(f ) > ρ holds, and let α ∈ (0 , 1) be the target error probability. Sample sizes are integers between zero and N . The lower-bound constructions use an unrestricted casewise candidate class, which can realize every binary loss pattern on U and includes candidates that recognize complete inputs and return their known specified outputs. For the upper bounds, candidate selection may be arbitrarily adaptive under the stated information conditions.

# 6 Empirical Case Study 

We evaluate how development tests change successive implementations of a stateful API. A paired design compares five policies from the same initial implementation, four added conditions refine that comparison, and every candidate is measured on a common private evaluation set. The experiment tests the development role of GTDD by comparing fixed tests with tests regenerated during repair, and it evaluates the acceptance rule afterwards on the recorded candidates. Four choices, each stated where it applies, distinguish this implementation from the protocol of Section 3: the coding model answers single requests without tool access and so cannot edit protected files, candidates run inside the evaluator’s 22 process under a wall-clock limit, reduction preserves any disagreement with the reference rather than the designated one, and no acceptance rule acts during the four rounds. 

# 6.1 Experimental Setup 

The task is a single-client, in-memory key-value store modeled on a subset of Redis. Its stateful behavior allows counterexamples to expose interactions among commands and makes repeated implementation changes measurable on the same collection of traces. 

Task and evaluation inputs. The interface has 61 commands in eight families: keys, strings, lists, hashes, sets, sorted sets, expiry under a logical clock, and transactions with optimistic watches. A 2 ,072-word specification fixes every reply and error code, including the order in which checks apply, and a 620-line reference implementation computes expected replies. We selected the task because initial implementations fail on a substantial fraction of traces while counterexample-based repair remains possible. Each evaluation trace applies 10 to 40 operations to a fresh service, each generated trace contains at most 40 operations, and a reduced trace is no longer than its original. The evaluation set consists of 2 ,000 traces drawn once from a fixed random generator and used for every condition and round without being reported to either model. Each candidate is imported into the evaluator’s process, which applies a limit of 0 .5 seconds of wall-clock time per trace. A reply is correct when it equals the reference reply as a JSON value, so a boolean never matches an integer. The harness that ran the trajectories, including the selection of counterexamples, compared replies with Python equality, under which a boolean matches an integer. Scoring every saved candidate again, each in a separate process under the same limit, reproduced every recorded count under that comparison exactly, and the JSON comparison changes the count of one candidate, the final module of one Dynamic blind trajectory, by 7 of the 2 ,000 traces. Every count reported below uses the JSON comparison. The changed module is the last of its trajectory, so every candidate that received feedback has the same count under both comparisons, and the counterexamples it received were selected under Python equality. The records of the five conditions consist of every candidate module, every generator the testing model wrote, the counterexamples reported in each round, and each candidate’s failure count on the evaluation set after each round, together with the outcome of every evaluation trace from this second scoring. 

Model and paired design. Both coding and testing use gpt-4.1-mini, snapshot 2025-04-14, through single requests without tool access. Temperature, nucleus sampling, and the seed are left at the API defaults, and a request that fails is retried up to three times. A coding request receives the specification, the current module, and the feedback, and returns a complete module that is committed before execution. Each of 30 blocks begins with a module generated from the specification alone. All five conditions share that block’s initial module and then perform three repair rounds, giving four coding rounds in total. Every condition receives the public example’s outcome, and all trajectories run for the prescribed four rounds without an acceptance gate. 23 Statistical analysis. The outcome is the evaluation failure rate after each round. The primary comparison is the within-block difference after round four between Dynamic in-formed and Static LLM, and the remaining contrasts are secondary and exploratory, without adjustment for multiplicity. # 7 Discussion 

The results assign complementary roles to generated tests, existing regression tests, and independent audits. Development uses concrete failures to improve the implementation, while acceptance requires a probability statement about the candidate currently under consideration. 

Development feedback. The paired experiment shows that Dynamic blind and Dynamic informed end with lower mean failure rates than Static LLM, whose tests were generated once by the same model. Their generators use previous counterexamples and request more traces over the repair rounds, and the added conditions, which change mainly one of these features at each step, produce intermediate rates with no detectable step, so the result compares complete development policies. Static property draws its inputs from the generator that produced the evaluation set; its strength shows the value of inputs whose distribution matches the target, and the dynamic policies, which never see that generator, end without a detectable difference from it. GTDD accommodates both sources and saves their verified cases for subsequent regression checks. 

Evidence for acceptance. Test visibility and feedback determine what an adaptive candidate can learn before acceptance. The exact known-test result describes unrestricted casewise adaptation, and the history bound accounts for the information returned by repeated 27 testing on hidden inputs. Fresh conditional sampling after commitment gives a direct bound for the current candidate, with separate allocations for repository acceptance and simultaneous family conclusions. Over an unbounded sequence, summable allocations preserve that interpretation as implementations change. Counterexample reduction makes failures easier to repair, while its mapping to original cases determines how much information the feedback reveals. 

The evaluation target. A fixed population gives an explicit target on which complete evaluation has no sampling error. The audit uses fewer cases to decide whether that target is met, and its sample size controls both false acceptance and the chance of accepting a candidate within tolerance. Table 4 makes this tradeoff visible for the zero-failure rule. For structured programs, the reference implementation defines the expected responses. For language and speech applications, the declared evaluation procedure defines the loss, so the choice of scenarios and judgments is part of the target itself. This formulation connects development tests to a precise acceptance claim. 

# 8 Conclusion 

We formulated GTDD as test-driven development in which a separate testing agent generates new inputs after each candidate is fixed and verified failures become feedback and regression tests. The finite-population analysis characterizes how known tests and repeated feedback affect false acceptance, and establishes fresh-audit guarantees for adaptive development. In the paired experiment, Dynamic blind and Dynamic informed ended with lower mean failure rates than Static LLM, further conditions did not attribute this difference to a single feature, source access produced no detectable additional gain, and property-based tests drawn from the evaluation distribution provided a strong baseline.

# B Counterexample Selection and Reduction 

Counterexample selection determines which observed failures guide the next coding round. Both rules choose at most k previously unreported development failures, using only the permitted information about those failures. 

Selection rules. The standard rule first favors a semantic family not yet selected in the round, then a failure mechanism not yet selected, and finally shorter traces and canonical identifiers. The compact-failure rule first favors shorter traces, then fewer distinct operations, and then families already reported in an earlier round, with canonical identifiers breaking ties. Both rules choose deterministically among the same observed failures. 

Reduction budget. A preliminary selection limits the reduction pool to 4 k original traces, each containing at most L operations, where L is the schema’s trace-length limit. Prefix search evaluates at most L prefixes. Each pass of single-operation deletion evaluates at most 

L variants and shortens the trace by one operation when successful, so at most L passes are possible. The reduction cost is therefore at most L + L2 candidate executions per original trace and 4 k(L + L2) per round. Every shorter trace is validated before execution and replaces the current trace only after it has been verified to exhibit the same designated failure. The selection rule is applied again 32 to the reduced pool, and the chosen reductions are included in both the feedback and the regression tests. Private links to the original traces support analysis of which case identities the reductions reveal.
